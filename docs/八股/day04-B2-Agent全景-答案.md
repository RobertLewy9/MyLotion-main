## Part 1 · 概念

### 1. LLM、Prompt、Context 是什么关系？

**一句话：**

LLM 是负责根据输入生成下一步输出的模型；Prompt 是给模型的指令；Context 是这一轮模型能看到的全部信息。

可以写成：

```text
Context = System Prompt + 历史 / 摘要 + 外部资料 + 当前用户输入
```

然后把 Context 交给模型，模型生成文本或工具调用。

**模型为什么没有记忆？**

模型本身不保存某一轮会话的状态。应用把历史消息存进数据库，下一次请求时重新拼成 `system + 历史 + 当前输入` 再发给模型。所谓多轮对话，是应用层做出来的，不是模型内部记住了上一轮。

### 2. Tool、Function Calling、MCP、Skill、Agent 在哪一层？

**一句话：**

模型负责决策，应用负责编排和执行，Tool 是最小动作，MCP 是接入标准，Skill 是做事方法，Agent 是带循环的执行系统。

| 名词 | 一句话定位 | 主要归属 |
|------|------------|----------|
| **Tool** | 一个具体能力，例如搜索、读文档、修改笔记 | 应用服务端 |
| **Function Calling** | 模型用结构化格式表达「我要调用哪个工具、传什么参数」 | 模型输出协议 |
| **MCP** | 应用连接外部工具/数据源的标准协议 | Host ↔ Server |
| **Skill** | 一组可复用的指令、知识和流程封装 | 宿主 / 平台侧 |
| **Agent** | 模型决策 + 工具执行 + 结果回填 + 继续判断的完整运行时 | 模型 + 应用 |

**一个工具调用怎样发生：**

1. 应用把工具的名称、用途和 JSON schema 交给模型；
2. 模型决定是否调用，并输出工具名和参数；
3. 服务端校验参数、权限和业务状态；
4. 服务端真正执行工具；
5. 工具结果作为 tool 消息回填模型；
6. 模型继续调用工具或输出最终答复。

模型不能直接访问数据库，也不会在模型内部执行工具。真正执行和权限校验都在应用侧，这一点讲错就会暴露对 Agent 链路的理解问题。

### 3. Agent Loop 与 Workflow

**Workflow**：步骤由代码提前规定，例如“先搜索、再读文档、最后生成摘要”是固定流水线。

**Agent Loop**：下一步由模型根据当前观察动态决定，可能连续调用多个工具，直到结束。

```text
模型判断
  → 不调用工具：返回最终答案
  → 调用工具：服务端执行并回填结果
  → 模型再次判断
```

**什么时候不需要 Agent？**

- 只需要一次分类、改写或总结；
- 流程固定，代码能明确按顺序执行；
- 对延迟、成本和可预测性要求很高；
- 操作只有一个确定步骤，例如直接调用 `renameNote(id, title)`。

**什么时候值得用 Agent？**

- 用户目标开放，不知道要查几次、查什么；
- 需要根据工具结果动态选择下一步；
- 需要组合多个数据源；
- 失败后要换策略继续尝试。

Agent 要有硬性的步数上限、超时和终止条件，不能只靠提示词说“不要无限循环”。

## Part 2 · MyLotion 的「一句话改一篇笔记」

### 完整链路

1. 用户在 AI 面板输入“把 Q3 计划里的时间改成下周五”；
2. 前端 POST `/api/ai/chat`，同时携带 `requestId`；
3. 服务端鉴权，执行幂等检查，组装 system prompt、历史摘要、最近原文和当前输入；
4. 调用 `streamText({ model, tools, stopWhen })` 开始 Agent Loop；
5. 模型先决定调用 `searchNotes` 找到目标文档，再调用 `readNote` 获取内容；
6. 服务端校验参数和 `userId`，执行工具，把结果回填模型；
7. 模型决定调用 `updateNote` 修改指定字段，服务端再次校验并写入数据库；
8. 修改产生的副作用通过 `onEvent` 上报，经 SSE 推给前端，侧边栏和编辑器刷新；
9. 模型不再调用工具，输出“已修改”的最终答复；
10. 如果是删除等不可逆操作，第一次只产生 `confirm_delete`，用户确认后才执行。

### 为什么这样分工？

- 模型擅长理解意图和选择工具，但不能直接拥有数据库权限；
- 服务端能校验 schema、`userId`、RLS、幂等和事务；
- 前端只根据事件刷新 UI，不需要知道模型内部如何思考；
- 危险操作把“准备”和“提交”拆开，用户必须看到影响范围再确认。

### 追问：重命名文档还需要 Agent 吗？

如果目标文档已经确定，重命名就是一个明确的一步操作，直接调用 `renameNote` 的 Workflow 更简单、可预测、成本更低。Agent 的价值在于“路径不确定、需要根据观察决定下一步”，不是把所有 CRUD 都套进循环。

## 60 秒版

LLM 是无状态的推理模型，Prompt 和 Context 由应用每次拼好再传进去。模型可以输出 Function Calling，但工具真正由服务端执行，结果再回填模型。Tool 是最小动作，MCP 负责接外部能力，Skill 是流程封装，Agent 是动态决策和执行循环。MyLotion 的用户请求先鉴权和组装上下文，再由 Agent 搜索、读取、修改文档，工具结果回填模型，副作用通过 `onEvent` 和 SSE 通知前端；删除等危险操作必须经过确认。只有路径不确定的任务才值得用 Agent，固定的单步操作用 Workflow 更合适。
