# Day 6 · B2 面试口述版：Agent、ReAct 与停止条件

答题顺序：**先说结论，再解释原因，最后结合 MyLotion 项目。**

## 1. Agent 和一次模型调用有什么区别？Agent 和 Workflow 呢？

**一句话结论：** 一次模型调用通常是输入上下文、生成输出；Agent 可以根据模型的判断调用工具、获取结果，再决定下一步；Workflow 则主要由代码预先编排执行流程。

**展开来说：**

- **一次模型调用：** 给模型输入，它返回文本或结构化结果，本身不会直接执行外部操作。
- **Agent：** 模型可以根据当前任务和工具返回的结果，决定下一步调用什么工具、传什么参数，以及是否继续。
- **Workflow：** 主要由代码控制执行顺序，比如先查询数据，再分类，最后生成结果。模型可以参与其中的某些步骤，但不一定负责决定整个流程。

核心区别是：**下一步主要由模型动态决定，还是由代码预先编排。**

Agent 更灵活，但执行路径和结果可能不那么确定；Workflow 更容易控制和测试，但面对开放任务时，灵活性可能不足。实际项目也经常把两者结合起来。

**结合 MyLotion：**

比如用户说“帮我找出性能优化相关的笔记，并归档”。Agent 可以先搜索，再读取笔记，最后归档；如果没有找到合适的笔记，也可以直接向用户说明情况。

这些步骤不是全部提前写死的，而是可以根据搜索结果动态调整，所以这部分具有 Agent 的特点。

## 2. ReAct 的循环是什么？为什么不能省略 Observe？

**一句话结论：** ReAct 可以概括为 Reason、Act、Observe，也就是推理、行动、观察结果，再根据结果决定下一步。

**展开来说：**

- **Reason：** 根据用户目标和已有上下文，判断下一步要做什么。
- **Act：** 模型提出工具调用，系统根据工具定义和参数执行对应操作。
- **Observe：** 把工具执行结果反馈给模型，让模型继续判断。

为什么 Observe 很重要？

因为模型只能根据已有上下文推理，不能仅凭推理就确认外部操作的真实结果。比如模型提出归档一篇笔记，并不代表笔记已经成功归档。系统需要把执行结果反馈回来，模型才能判断操作是否成功，以及是否需要重试或调整方案。

**结合 MyLotion：**

模型调用 `searchNotes` 后，服务端执行搜索，并把搜索结果返回给模型。模型再根据结果决定是否调用 `archiveNote`。归档完成后，还需要根据实际执行结果判断操作是否成功。

## 3. Agent Loop 有哪些停止条件？只设步数上限够不够？

**一句话结论：** 常见的停止条件包括模型不再请求工具、达到最大执行步数，以及超时、用户取消等外部中断。具体业务也可以设置额外的终止条件。

**展开来说：**

1. **模型结束工具调用：** 模型不再请求工具，生成最终回答，流程正常结束。
2. **达到步数上限：** 限制 Agent 连续执行的轮数，避免无限循环或过度调用工具。
3. **命中业务终止条件：** 比如工作流中的 `finish` 工具明确表示任务结束。这需要系统专门实现，不能假设所有 SDK 都会自动识别任意终止工具。
4. **外部中断：** 比如请求超时、用户取消，或者达到 token、费用等预算限制。

只设置步数上限还不够，因为它只能限制执行次数，不能保证任务完成，也不能保证每一步都有效。

例如，模型可能连续搜索同一个关键词，浪费执行次数；也可能搜索成功了，却没有完成后续归档。

因此，还可以增加重复调用检测、工具超时、结果校验，以及删除等危险操作的用户确认。

**结合 MyLotion：**

项目可以通过 `stopWhen` 限制 Agent 的执行步数，通过工具级超时限制单次调用耗时，并对删除操作设置确认流程。这些机制分别控制循环次数、单次调用时间和高风险操作。

具体的步数上限、超时配置是否已经在项目中完整实现，需要以实际代码为准。

## 4. MyLotion 中的 `streamText({ model, tools, stopWhen })` 如何实现 ReAct？

**一句话结论：** `streamText` 是 AI SDK 提供的流式生成接口；结合工具定义和停止条件，可以编排模型多轮生成与工具调用，形成 Agent 执行循环。

**完整流程：**

1. 服务端整理系统提示词、历史摘要、最近的对话记录和当前用户输入，并配置可用工具。
2. 模型判断需要搜索笔记，于是发起 `searchNotes` 工具调用。
3. SDK 根据工具定义协调调用流程，服务端执行搜索工具，并将执行结果加入后续模型上下文。
4. 模型根据搜索结果继续判断，可能调用 `archiveNote`，也可能直接生成回答。
5. 工具执行期间，业务代码可以通过 `onEvent` 等机制上报笔记变更事件，再由 SSE 将事件推送给前端。
6. 当模型不再请求工具，或者达到配置的停止条件时，本轮 Agent 执行结束。

这里要区分两条链路：**工具调用链路负责执行任务，SSE 事件链路负责向前端传递进度和操作结果。** 工具上报一个 `note_modified` 事件，并不等于模型已经收到这个事件作为下一轮推理的上下文；这取决于项目具体实现。

**为什么用 SDK，而不是自己写 `while` 循环？**

如果自己实现，就要处理模型请求、工具调用参数、消息格式、结果回填、流式输出、异常和取消等细节。SDK 封装了其中很多流程，我们主要负责定义工具、配置停止条件，并处理业务逻辑和副作用。

不过，SDK 并不会自动替我们决定所有业务规则。例如，哪些操作必须确认、如何验证任务是否真正完成，都需要应用自己设计。

## 追问一：模型连续三次调用同一个工具，参数也完全一样，怎么办？

先判断重复调用是否合理。如果工具本身是幂等的，重复执行可能不会产生额外副作用，但仍然会浪费资源。

可以在循环层记录工具名称和参数，对明显重复的调用进行检测，并把提示性错误或已有结果反馈给模型，让它尝试其他方案。如果仍然重复，就终止本轮执行。

但不能简单规定第二次重复调用就一定报错，因为有些工具可能确实需要重复执行。

## 追问二：工具报错，是返回前端还是反馈给模型？

通常应该区分两种情况。

如果错误是模型可以利用的信息，比如搜索条件不合法，可以将错误转换成清晰、可控的工具结果，让模型决定是否修正参数或尝试其他方案。

如果是服务端内部异常，则应记录详细日志，并向模型或前端返回经过处理的错误信息，避免泄露堆栈、密钥等内部细节。

具体错误如何回传，要看工具封装和 SDK 的异常处理方式，不能认为所有异常都应该交给模型重试。

## 三条面试金句

1. **Agent 和 Workflow 的核心区别，是执行路径主要由模型动态决定，还是由代码预先编排。**
2. **Observe 的作用是把真实执行结果反馈给模型，让它基于结果调整下一步，而不是只靠推理猜测。**
3. **步数上限只能限制执行次数，不能保证任务完成，所以还需要超时、重复调用检测和结果校验等机制。**
