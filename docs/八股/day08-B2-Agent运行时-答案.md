# Day 8 · B2 轨答案 —— Agent 运行时：循环、重试与确认闸门（面经校准版）

> **归属：Day 8 · B2 轨（Agent 八股）**
> 依据：8 场面经中的 AI 追问集中在工具、MCP 和项目落地；本页不背 ReAct 术语，只回答 Agent 真正运行时最容易被追问的三件事。
> 回答顺序：先说循环，再说失败与幂等，最后说危险操作的人类确认。

## Part 1 · 概念

### 1. 一次模型调用 vs Agent Loop

**一句话：**

一次模型调用是「输入一次、输出一次」；Agent Loop 是「模型决定下一步 → 应用执行工具 → 把结果交给模型 → 模型再决定」的循环。

```text
用户输入
  -> 模型
     -> 不再调用工具：输出最终答案，结束
     -> 返回 tool call：服务端校验并执行
                         -> 工具结果回填
                         -> 回到模型继续判断
```

**继续的条件**：模型这一轮明确要求调用工具，而且参数能通过校验。

**停止条件**：

1. 模型不再请求工具，给出最终答案；
2. 达到最大步数，例如 8 或 10 步；
3. 命中终止工具，例如任务完成或明确失败；
4. 超过时间 / token 预算，或用户主动 abort；
5. 出现权限错误等不可恢复异常。

**工程上防止跑飞：**

- 最大步数是硬上限，不能只靠提示词说“不要无限调用”；
- 设置单次请求的超时和 token 预算；
- 对「工具名 + 参数」做重复检测，连续相同调用直接终止；
- 参数校验失败只允许有限次纠正，不允许模型无限重试；
- 记录每一步工具调用，方便排查成本和异常。

**顺手区分 Workflow**：Workflow 的步骤通常由代码预先规定；Agent 的下一步由模型根据工具结果动态决定。不是所有固定流程都值得套 Agent。

### 2. 工具失败、超时与重复调用

**一句话：**

模型只负责提出工具调用，服务端负责校验、执行和错误分类；能纠正的错误回填模型，不能纠正的错误直接终止。

| 错误类型 | 例子 | 处理方式 |
|----------|------|----------|
| 参数错误 | 缺少 `documentId`、字段类型不对 | 把结构化错误回填模型，允许有限次纠正 |
| 业务未命中 | 文档不存在、搜索无结果 | 作为正常工具结果返回，让模型换策略或向用户说明 |
| 权限错误 | 文档不属于当前用户、RLS 拒绝 | 立即终止该操作，记录日志，不把删库权限交给模型碰运气 |
| 瞬时故障 | 网络抖动、数据库超时 | 仅对幂等读操作做有限重试；写操作必须带幂等键 |
| 超时 / abort | 工具执行超时、用户取消 | 取消下游请求，返回结构化结果；不要继续执行已失去上下文的操作 |

**幂等的核心**：同一个逻辑操作执行一次和执行多次，最终效果相同。

工程上至少准备三层：

1. **整个 Agent 运行**用 `requestId` 去重，用户连点两次发送只创建一次运行；
2. **单个工具调用**携带 `toolCallId` 或业务 operation id，重试时复用同一个 id；
3. **数据库写操作**用唯一约束 / 条件更新兜底，例如 `(userId, requestId)` 唯一，重复请求返回已有结果。

实践里很难做到“绝不重复投递”，更现实的是：**允许至少一次到达，但通过幂等让副作用只发生一次。**

### 3. 危险工具的 human-in-the-loop

**一句话：**

模型可以提出「我想删除」，但不能拥有最终执行权；不可逆操作必须由用户在服务端可验证的确认流程中批准。

**为什么不能直接删：**

- 模型可能理解错用户意图；
- 用户输入或工具返回的文本可能夹带提示注入；
- 模型可能把“整理一下”误判成“删除”；
- 即使模型判断正确，用户也应该先看到删除范围。

**两阶段确认：**

```text
模型调用 deleteNote(id)
  -> 服务端只做校验，不删除
  -> 生成确认信息：标题、影响数量、版本号、一次性 token、过期时间
  -> onEvent(confirm_delete, ...) -> SSE -> 前端弹确认框
  -> 用户点击确认
  -> POST 携带 token + requestId
  -> 服务端再次校验 userId / RLS / 资源版本 / token 是否已使用
  -> 事务内执行删除 + 写审计日志
  -> 重复确认直接返回第一次结果，不重复删除
```

**关键点：**

- 确认框不是权限系统；最终权限必须在服务端校验；
- 第一次工具调用不产生业务副作用，只产生待确认操作；
- 第一次工具结果回填模型的是 `awaiting_confirmation`，提示它等待用户，而不是继续重复调用 `deleteNote`；
- 确认 token 一次性、短时效，并绑定资源和用户；
- 确认前资源被修改或移动时，重新提示，不能拿旧预览直接执行；
- 批量删除或子文档删除要明确影响范围；
- 所有危险操作写审计日志，方便追查是谁、何时、删了什么。

## Part 2 · MyLotion 的 Agent 主链路

### 完整流程

1. 前端提交问题，并携带 `requestId`；
2. `/api/ai/chat` 先鉴权，再按 `requestId` 做幂等检查，组装系统提示词、摘要、最近历史和当前输入；
3. `streamText({ model, tools, stopWhen })` 启动 Agent Loop，同时设最大步数和超时；
4. 模型返回 `searchNotes`、`readNote`、`updateNote`、`deleteNote` 等工具调用；
5. 服务端按 schema 校验参数，并带 `userId` 查询或修改数据，工具结果作为 tool 消息回填模型；
6. 有副作用的操作通过 `onEvent` 上报，例如 `note_modified`；危险操作只上报 `confirm_delete`，此时数据库不变；
7. 事件经 SSE 推给前端：文本进入对话区，进度显示当前工具，`note_modified` 触发列表刷新，`confirm_delete` 弹确认框；
8. 模型不再调用工具后输出最终答复，结束本次运行。

### 追问：用户连点两次发送怎么办？

前端可以先禁用按钮，但这只能减少重复，不能作为最终保证。服务端还要用 `requestId` 唯一约束或幂等表拦截；第二次请求直接返回第一次的 run id / 状态，不再启动新的 Agent。

### 追问：确认框被点两次怎么办？

确认接口同样要幂等：确认 token 只能消费一次，删除操作使用同一个 operation id，数据库唯一约束或事务状态保证重复请求返回第一次结果。不能把“前端弹窗只点了一次”当成幂等保障。

### 追问：为什么危险操作只发事件，不在工具里直接删？

因为工具执行发生在服务端，前端必须知道“模型准备做什么”才能让用户批准。把「准备」与「提交」拆开，既能让用户看到影响范围，也能在服务端重新校验权限和资源状态，避免模型或过期页面直接触发不可逆操作。

## 60 秒版

MyLotion 每次请求先按 `requestId` 幂等落库，再组装上下文启动 Agent Loop。模型只决定调用哪个工具和参数，服务端校验 `userId` 后执行，并把结果回填模型。普通修改通过 `onEvent` 上报，前端刷新；删除这类危险操作第一次只生成 `confirm_delete`，用户确认后服务端再次校验并幂等执行。这样循环有步数上限，失败有分类处理，重复请求也不会产生重复副作用。

- 能区分参数错误、权限错误、瞬时故障和超时的处理方式；
- 能讲清 `requestId`、`toolCallId` 和数据库唯一约束分别防什么；
- 能完整讲出 `deleteNote` 的两阶段确认流程。
