# Day 8 · B2 轨答案 —— Agent 运行时：循环、重试与确认闸门

**核心：** Agent 运行时主要解决三个问题：怎么循环调用工具、工具失败或重复调用怎么办、危险操作如何让用户确认。

## Part 1 · 概念

### 1. 一次模型调用 vs Agent Loop

**一句话：**

一次模型调用是输入一次、输出一次；Agent Loop 是模型决定调用工具，服务端执行后把结果交回模型，模型继续判断，直到任务结束。

```text
用户输入
  → 模型
  → 判断是否调用工具
      → 不调用：输出最终答案，结束
      → 调用工具：服务端执行
          → 工具结果回填模型
          → 模型继续判断
```

**什么时候停止？**

1. 模型输出最终答案，不再调用工具。
2. 达到最大步数，例如 8 步。
3. 超过时间或 Token 预算。
4. 用户主动取消，或遇到不可恢复错误。

**怎么防止无限循环？**

- 设置最大步数和超时。
- 检测重复的工具调用。
- 参数错误只允许有限次纠正。

**顺便区分 Workflow：** Workflow 的步骤由代码提前规定；Agent 的下一步由模型根据执行结果动态决定。

### 2. 工具失败、超时与重复调用

**一句话：**

模型负责提出工具调用，服务端负责参数校验、权限检查、执行和错误处理。

| 错误类型 | 处理方式 |
|---|---|
| 参数错误 | 返回错误信息，让模型有限次纠正 |
| 业务未命中 | 返回正常结果，让模型换策略或告知用户 |
| 权限错误 | 拒绝操作，不能让模型反复尝试 |
| 瞬时故障 | 读操作可有限重试，写操作需要幂等保护 |
| 超时 / 取消 | 停止后续执行，取消下游请求 |

**什么是幂等？**

同一个操作执行一次和执行多次，最终效果相同，避免重复创建、修改或删除。

主要有三层：

1. `requestId`：防止同一次用户请求启动多个 Agent。
2. `toolCallId / operationId`：识别工具调用或业务操作，重试时复用稳定的操作 ID。
3. 数据库唯一约束 / 事务：防止重复写入，作为最终保障。

**记住：** 网络请求可能重复到达，但要保证业务副作用只发生一次。

### 3. 危险工具的 Human-in-the-loop

**一句话：**

模型可以提出删除请求，但不能直接执行不可逆操作，必须经过用户确认和服务端再次校验。

**为什么需要确认？**

- 模型可能理解错用户意图。
- 用户可能没有意识到删除范围。
- 模型可能受到提示注入影响。

**两阶段确认：**

```text
模型调用 deleteNote
  → 服务端校验参数，不执行删除
  → 生成待确认操作和确认信息
  → SSE 通知前端弹出确认框
  → 用户点击确认
  → 前端提交确认请求
  → 服务端再次校验权限、资源状态和确认 token
  → 执行删除，记录审计日志
```

**关键点：**

- 第一次调用只生成待确认操作，不产生删除副作用。
- 确认 token 要绑定用户和资源，并设置有效期、只能使用一次。
- 用户确认后，服务端必须重新检查权限和资源状态。
- 重复确认要通过幂等机制避免重复执行。
- 批量删除要明确展示影响范围。

## Part 2 · MyLotion 的 Agent 主链路

### 1. 完整流程

```text
前端提交问题 + requestId
  → /api/ai/chat
  → 鉴权、幂等检查、组装上下文
  → streamText 启动 Agent Loop
  → 模型选择工具
  → 服务端校验参数和 userId
  → 执行工具并回填结果
  → 模型继续判断
  → 输出最终答案
```

**事件如何通知前端？**

- `onEvent`：上报工具执行过程中的事件。
- SSE：将事件推送到前端。
- `note_modified`：通知前端刷新文档列表。
- `confirm_delete`：通知前端弹出删除确认框。

注意：删除工具第一次调用只产生 `confirm_delete` 事件，不直接删除数据库数据。

### 2. 面试追问

**追问一：用户连点两次发送怎么办？**

前端可以禁用发送按钮，但真正的保障在服务端：通过 `requestId` 做幂等检查，重复请求返回已有运行状态，不再启动新的 Agent。

**追问二：确认框被点两次怎么办？**

确认 token 只能消费一次，数据库通过事务和幂等机制保证删除不会重复执行。

**追问三：为什么不在 deleteNote 工具里直接删除？**

因为模型不应该拥有不可逆操作的最终执行权。先生成待确认操作，让用户看到删除范围，确认后再由服务端检查权限并执行。

## 60 秒版

MyLotion 的 Agent 采用循环调用机制：模型决定调用哪个工具，服务端校验参数和用户权限后执行，再把工具结果回填模型，直到模型输出最终答案。

运行过程中设置最大步数和超时，避免无限循环；工具失败按参数错误、权限错误和瞬时故障分类处理；通过 `requestId` 和数据库幂等机制避免重复操作。

对于删除这类危险操作，第一次调用不直接执行，而是通过 SSE 通知前端弹出确认框。用户确认后，服务端再次校验权限和资源状态，再执行删除。

**核心就是：模型负责决策，服务端负责执行和安全控制，用户负责批准危险操作。**
