## Part 1 · 概念（口述要点）

**Q1 模型**：同步代码在调用栈跑完 → **清空微任务队列（直到空）** → 浏览器有机会渲染 → 取**一个**宏任务执行 → 再回到清空微任务 → 循环。
订正一个措辞：不是"执行第一个宏任务队列"，而是**每轮只取一个宏任务**。

**Q2 清单**（这题面经直接问，要背全）

- 微任务：`Promise.then/catch/finally`、`async/await`（await 之后的部分）、`queueMicrotask`、`MutationObserver`（浏览器）、`process.nextTick`（Node，优先级更高）
- 宏任务：`setTimeout` / `setInterval`、`setImmediate`（Node）、I/O 回调、UI 事件回调（点击等）、网络请求回调

**Q3**：它是宏任务，要等同步代码 + 微任务清空后才轮得到。补充两点：`setTimeout(fn, 0)` 实际有 **4ms 最小延迟**（嵌套 ≥5 层的定时器被强制 clamp），所以"0"不等于"立刻"。

**Q4**：同步代码执行完后清空；清空过程中新产生的微任务**入队尾**，本轮一起清完（所以"清空"是循环直到真空，不是扫一遍）。

**Q5（原答错了）**：渲染**不在同步代码阶段**，而在**宏任务之间**——「微任务清空之后、下一个宏任务开始之前」。
卡页面的原因也要反过来讲：**是微任务挡住了渲染**，不是"宏任务等不到执行"。微任务队列不清空，浏览器就没机会进入渲染步骤。

**Q6**：微任务。因为 `await` 本质是把后面的代码包成 `then` 回调，等 promise 落定后被调度。

**Q7（只答了一半）**：

- 微任务无限递归 → 事件循环**永远卡在"清空微任务"这一步**：不渲染、不响应输入（页面彻底冻结），而且**不报错**，CPU 打满
- 宏任务无限递归（如 `setTimeout` 自己调自己）→ 每轮宏任务之间**浏览器都有机会渲染和响应**，页面看起来是正常的
- 本质区别：**渲染窗口只存在于宏任务之间**

## Part 2 · 输出题标准答案

| 题 | 标准答案 | 一句话理由 |
|----|----------|------------|
| Q1 | `start → end → promise → timeout` | 同步 → 清空微任务 → 取一个宏任务 |
| Q2 | `A → E → C → D → B` | 同上；`then` 链上每一级都是一个独立微任务 |
| Q3 | `1 → 3 → 4 → 5 → 2` | `return Promise.resolve()` 要多等 **2 个 tick**，另一条链的 3/4/5 抢在前面 |
| Q4 | `f → sync → then` | `async` 函数体同步执行到第一个 `await`；`return 1` = 用 1 兑现它返回的 promise，`then` 走微任务 |
| Q5 | `s1 → y1 → x → s2 → y2` | **`await` 右边的表达式是立即求值的**：`x()` 先被同步调用（打印 x），才轮到让位 |
| Q6 | `sync → m1 → m3 → m2 → t1` | m2 是 m1 里新排的，要等本轮已有的 m3 跑完 |
| Q7 | `qm → p → st` | `queueMicrotask` 和 `then` 同级，先注册先跑 |
| Q8 | `a → await thenable → b → c` | `await` 一个 **thenable** 多等一轮，同步注册的 `a` 先跑 |
| Q9 | `sync → t1 → m-in-t1 → t2` | 每个宏任务跑完都清一次微任务 |
| Q10 | `1 → 2 → 5 → 3 → 4` | **`new Promise(executor)` 的 executor 是同步执行的** |
| Q11 | `a → c → b → d` | `await` 让位排的微任务，早于后面注册的 `then` |
| Q12 | `sync → outer → inner` | 内层定时器在下一轮宏任务 |

**Q3 的规律（实测对比）**

```js
// return 普通值 → 多 1 个 tick
Promise.resolve().then(() => { log("1"); return "x"; }).then(() => log("2"));
Promise.resolve().then(() => log("3")).then(() => log("4")).then(() => log("5"));
// → 1 → 3 → 2 → 4 → 5

// return Promise / thenable → 多 2 个 tick
Promise.resolve().then(() => { log("1"); return Promise.resolve("x"); }).then(() => log("2"));
// → 1 → 3 → 4 → 5 → 2
```

**Q8 的写法解释**：`{ then(res) { res(); } }` 是一个「长得像 promise 的普通对象」（thenable）。
按规范，`await` 一个 thenable 会**调用它的 `then` 方法，并把一个 `resolve` 函数当作参数传进去**。
所以 `then(res) { res(); }` 里的 `res` 就是"我完成了"这个动作——调用 `res()` 表示这个 thenable 兑现了。
因为它不是**原生 promise**，引擎要多走一遍解析流程，所以慢一个 tick。

## Part 3 · 场景题参考答法

**S1（微任务合并）**

```js
let scheduled = false;
const dirty = new Set();
function notify(id) {
  dirty.add(id);
  if (scheduled) return;
  scheduled = true;
  Promise.resolve().then(() => {
    scheduled = false;
    flush([...dirty]); // 只通知一次
    dirty.clear();
  });
}
```

关键要讲清**「一秒改 3 次」是哪种 3 次**：

- 如果是**同一次同步操作里**改了 3 个字段/3 个订阅者 → 微任务合并正好，3 次 notify 合成 1 次
- 如果是**用户一秒内敲了 3 次**（3 个不同宏任务）→ 微任务合并**管不了**，那要用 debounce / 节流

**为什么不用 `setTimeout(0)`**：

1. `setTimeout(0)` 是**下一轮宏任务**，中间浏览器有机会渲染 → 中间态会闪一下；微任务在渲染之前跑完，中间态**根本不会被画出来**
2. 定时器有 **4ms 最小延迟**，还可能被别的宏任务插队 → 通知时机不可控
3. 语义上要的是"这一轮改完就通知"，微任务正好等于"本轮末尾"

**它既不是防抖也不是节流**：防抖是"等用户停下来"，节流是"固定间隔放一次"，微任务合并是"同一个 tick 内去重"——不引入任何人为延迟。

**S2（原答方向反了）**

- 微任务**压不住渲染**：微任务在**渲染之前**清空，用它做的 flush 依然每轮都跑，渲染次数一点没少
- 正确做法：把 token 攒进 buffer，用 **`requestAnimationFrame`（帧对齐）或 16ms 节流**一次性写入 → 渲染次数从"每个 token 一次"降到"每帧最多一次"
- React 18 自动批处理：**同一个宏任务内**的多次 `setState` 只渲染一次。但 SSE 的 100 个 token 来自 **100 个不同宏任务**，自动批处理救不了 → 必须自己 buffer + 帧对齐

**S3（debounce vs 微任务合并）**

- 触发条件：debounce 靠**时间**（停止 N ms 后），微任务合并靠**tick**（同一轮同步代码结束）
- 延迟：debounce 一定有延迟；微任务合并几乎零延迟
- 场景：debounce → 用户输入、窗口 resize、搜索联想；微任务合并 → 程序内部的多次状态变更只通知一次
- debounce 用微任务实现的后果：两次点击之间隔着异步，就不会被合并（**该防的没防住**），而且没法表达"等用户停下来"

## Part 4 · 追问答案

**Z1**：`process.nextTick` **先**（实测，与注册顺序无关）。Node 在每个阶段结束后、清空 Promise 微任务**之前**先清空 nextTick 队列。
为什么单独搞一条：它**早于 Promise 标准化**；用途是"在**当前操作彻底结束、进入下一个阶段之前**立刻修正状态"（例如给用户返回前先发事件、把参数补全），保证 I/O 开始前状态已就绪。
代价：递归 `nextTick` 会**饿死 I/O**（定时器和网络回调永远轮不到）——和微任务死循环卡死渲染是同一个道理。

**Z2**：**不止一条**。浏览器有多个 task source（定时器、用户交互、网络、DOM 操作），各自是独立队列，**浏览器自行决定取哪个**，所以不是全局 FIFO。
`setTimeout` 到点不一定立刻执行——主线程忙就排队。
「4ms 最小延迟」：HTML 规范规定嵌套层级 ≥5 的定时器最少 4ms（防止定时器密集递归）；后台标签页会被节流到 1000ms。
「定时器饥饿」：如果一直有更"紧急"的任务（用户输入、渲染）插进来，定时器回调会被无限推迟。

**Z3**：微任务清不完 → 卡在清空阶段，**渲染彻底没机会**，页面冻结、CPU 打满，而且没有新宏任务所以看起来像"死机"。
宏任务排不完 → 每轮之间有渲染窗口，页面**仍然能滚动、能点击**，只是回调延迟变大。
**渲染窗口只存在于宏任务之间** —— 这就是两者的本质区别。

**Z4**：这题**算超纲**（面经没有「React 18 批处理」这个措辞），但底下的知识点有人问——腾讯云智一面问过「React 中 `setState` 的状态生效是在什么时候？」。
一句话答案：`setState` 只标记"有更新"，真正的重新渲染由调度器在**当前宏任务结束时**统一执行。
React 18 的自动批处理把「同一个宏任务内」的多次 `setState` 合并成一次渲染，所以放在 `setTimeout` 里的两次也能合并；React 17 只在 React 事件处理函数里批处理，`setTimeout` 里会渲染两次。

## 附 1 · tick 到底是什么

**tick = 微任务队列里「处理一个任务」的一次调度。**
通俗讲：代码「让位」一次（不立刻继续，而是排到队尾再等一轮），就是一个 tick。

> 别和另一种用法混：有的资料把「一次 Event Loop 循环（取一个宏任务 + 清空微任务）」叫一个 tick。
> 本文一律指**一次微任务调度**。

## 附 2 · 为什么 `return Promise` 是「多等 2 个 tick」

把微任务队列看成一条 **FIFO 队伍**，只有两条规则：

1. 同步代码里排进去的，按顺序进队
2. 一个任务执行时**新排**的任务，加在**队尾**

`then` 里返回值，下一级 `then` 什么时候被叫，取决于返回的是什么：

- `return 普通值` → 1 步：把值交给下一级，下一级排到队尾
- `return Promise` / thenable → 3 步：要「解析」这个 promise（先调用它的 `then`，等它落定，再触发下一级）

**Q3 逐步推演（普通值）**

| 步 | 处理 | 输出 | 队列 |
|----|------|------|------|
| 1 | J1：打印 1，返回 `"x"` | 1 | `[A1, J2]` |
| 2 | A1：打印 3 | 3 | `[J2, A2]` |
| 3 | J2：打印 2 | 2 | `[A2]` |
| 4 | A2：打印 4 | 4 | `[A3]` |
| 5 | A3：打印 5 | 5 | `[]` |

→ `1 → 3 → 2 → 4 → 5`

**Q3 逐步推演（return Promise）**

| 步 | 处理 | 输出 | 队列 |
|----|------|------|------|
| 1 | J1：打印 1，返回 P | 1 | `[A1, JX]` |
| 2 | A1：打印 3 | 3 | `[JX, A2]` |
| 3 | JX：调用 `P.then` | — | `[A2, JY]` |
| 4 | A2：打印 4 | 4 | `[JY, A3]` |
| 5 | JY：触发下一级 | — | `[A3, J2]` |
| 6 | A3：打印 5 | 5 | `[J2]` |
| 7 | J2：打印 2 | 2 | `[]` |

→ `1 → 3 → 4 → 5 → 2`

**怎么「量」出多等 2 个 tick**：放一条「每个 tick 走一步」的对照链当尺子（A→B→C→D→E），实测：

```js
// return 普通值：2 紧跟在 A 后面
1 → A → 2 → B → C → D → E

// return Promise：2 被推后 2 个位置
1 → A → B → C → 2 → D → E
```

## 附 3 · 微任务合并到底合的是什么

类比：微信把「3 条新消息」合并成一条通知 —— 不是不通知，是**同一小段时间内的多次变更只通知一次**。

```js
function makeNotify(onFlush) {
  let scheduled = false;   // 已经排了一个 flush，别重复排
  const dirty = new Set(); // 这一轮里哪些东西变了
  return (id) => {
    dirty.add(id);
    if (scheduled) return;         // 排过了，只记一笔就走
    scheduled = true;
    Promise.resolve().then(() => { // 排到本轮微任务队列
      scheduled = false;
      onFlush([...dirty]);         // 到这儿只通知一次
      dirty.clear();
    });
  };
}
```

推演（同一次同步操作里改 3 次）：

| 调用 | dirty | scheduled | 做了什么 |
|------|-------|-----------|----------|
| `notify("doc1")` | `{doc1}` | false → true | 排一个 flush |
| `notify("doc1")` | `{doc1}` | true | 只记录，直接 return |
| `notify("doc1")` | `{doc1}` | true | 只记录，直接 return |
| 同步代码结束 → 清空微任务 | | | **flush 跑 1 次** |

实测：同一轮改 3 次 → 通知 **1** 次。

**但它会失效**：3 次改动来自 3 个不同宏任务时，每次宏任务结束都会清空微任务 → flush 跑 3 次。
实测：3 个 `setTimeout` 各改 1 次 → 通知 **3** 次 → 这种情况要用 debounce。

## 附 4 · 微任务合并 vs debounce

| | 微任务合并 | debounce |
|---|---|---|
| 触发条件 | 这一轮同步代码跑完 | 停止操作 N ms 后 |
| 延迟 | 几乎没有 | 固定 N ms（如 300ms） |
| 合并范围 | 同一轮内的多次调用 | 一个时间窗口内的所有调用 |
| 典型场景 | 一次操作改了多个字段只通知一次；缓存失效标记；React `setState` 批处理 | 搜索框联想；窗口 resize；编辑器自动保存 |
| 类比 | 微信把 3 条消息合成一条通知，**立刻弹** | 等人不说话 300ms 才回应 |

判别口诀：**这几次调用是不是「同一轮代码」里发生的？**
是 → 微任务合并；否（来自用户点击 / 网络回调 / 定时器等独立事件）→ debounce / 节流。

## 附 5 · 4ms 最小延迟与定时器饥饿（通俗版）

**4ms 最小延迟**：规范规定，**同一个定时器嵌套超过 5 层后，最小间隔被强制为 4ms**，
防止「定时器递归」把 CPU 占满。类比：电梯按钮有最小反应间隔，防止你狂按。

> 实测补充：本机（Windows）嵌套 `setTimeout(fn, 0)` 的实际间隔是 **10~15ms**，
> 因为 Windows 的定时器精度本身就约 15.6ms。所以 `setTimeout(0)` 离「立刻」很远 ——
> 这恰恰说明「要立刻」就必须用微任务。另外，后台标签页的定时器会被节流到 1000ms。

**定时器饥饿**：定时器回调要**排队**，到点了不代表能跑。类比：食堂打饭，你排到了但一直被插队。
实测证据：

- 微任务连排 20 万次（耗时 11ms）**期间**，一个 `setTimeout(0)` **完全没机会执行**；微任务链结束后才跑起来
- 对照：宏任务递归 5 轮时，另一个 `setTimeout(0)` **立刻**就跑了

结论：**渲染和「别人的机会窗口」只存在于宏任务之间** —— 这就是微任务写多了会卡页面的实证。
