```text
记忆与 RAG

│  ├─ 短期：当前请求 / 会话，messages、滑动窗口、摘要

   ├─ 混合检索：向量 + 关键词（BM25）
   └─ 权限过滤、引用、评测与成本
```

## Part 1 · 概念

### Q1. 短期记忆和长期记忆有什么区别？分别怎么存、怎么放进上下文？

**参考答案（口述）**

记忆不是“模型自己记住了”，而是应用把需要的信息重新放进上下文。

| 维度 | 短期记忆 | 长期记忆 |
|---|---|---|
| 范围 | 当前请求 / 当前会话 | 跨会话、跨设备 |
| 典型内容 | 最近几轮消息、当前文档、工具结果 | 用户偏好、长期事实、历史结论 |
| 存放 | 消息数组、请求上下文、会话表 | 结构化数据库、向量库或混合存储 |
| 使用方式 | 按时间顺序保留最近内容 | 按相关性检索后再注入 |
| 主要问题 | 上下文窗口有限、成本上涨 | 怎么抽取、更新、去重和召回 |

**短期记忆的常见处理：**

1. 最近 N 轮原文直接保留；
2. 更早内容做摘要，保留目标、约束、已确认事实；
3. 当前选中的文档或工具结果作为额外上下文；
4. 超过 token 预算时先淘汰低价值内容。

**长期记忆的常见处理：**

- 明确事实放结构化表，例如“用户偏好中文回答”；
- 大段知识放文档库，切片后做向量检索；
- 写入前做去重和冲突处理，重要事实要能更新；
- 每次只召回相关内容，不能把整库都塞进 prompt。

**一句话：** 短期记忆解决“这次对话别忘了”，长期记忆解决“下次见面还记得”，最终都要经过筛选再进入上下文。

### Q2. RAG 是什么、为什么需要？embedding 和向量检索在其中起什么作用？

**参考答案（口述）**

RAG 是检索增强生成：先从外部知识库找相关资料，再把资料和问题一起交给模型生成答案。

**为什么需要：**

- 模型不知道公司内部文档和用户私有笔记；
- 模型知识可能过时；
- 直接微调成本高，数据更新也不方便；
- 检索结果可以附引用，方便核对；
- 让回答基于给定材料，降低胡编的概率，但不能保证零幻觉。

**完整链路：**

```text
离线建库
文档 → 清洗 → 切 chunk → embedding → 向量库 / 索引

在线问答
用户问题 → query embedding
  → 向量检索 top-k
  →（可选）关键词检索 + rerank
  → 权限过滤、去重、截断
  → 拼进 prompt → 模型生成 → 返回引用
```

**embedding 是什么：** 把文本映射成高维向量，语义相近的文本向量距离更近。常见相似度是余弦相似度：

```text
cos(a, b) = (a · b) / (|a| × |b|)
```

值越接近 1，方向越相似。它不是判断事实真假，只是判断语义相关性。

**向量检索：** 把 query 也转成向量，在库里找最相近的 top-k 个 chunk。数据量大时用近似最近邻索引（ANN）换速度。

**关键边界：** 检索回来不等于一定能回答；还要做权限过滤、相关性阈值、上下文长度控制和引用校验。

### Q3. chunk 怎么切、为什么要有 overlap？混合检索和 rerank 又解决什么问题？

**参考答案（口述）**

**chunk 是检索的基本单位。** 切得太大，噪声多、占 token；切得太小，语义不完整、召回碎片化。

常见策略：

- 按标题、段落、列表等结构切；
- 按固定 token 数切，并保留适量 overlap；
- 表格、代码块尽量不拆断；
- 给每个 chunk 带上文档标题、章节路径、更新时间等元数据。

**为什么要 overlap：** 防止关键句刚好跨在切分边界上。例如上一块结尾是“退款条件为”，下一块开头是“七天无理由”，没有重叠时两块都不完整。overlap 通常取 chunk 的 10%～20%，太大则重复和成本上升。

**混合检索：**

| 方式 | 强项 | 弱项 |
|---|---|---|
| 向量检索 | 语义相近、换一种说法也能找到 | 专有名词、编号、精确短语可能不稳 |
| 关键词检索（BM25） | 精确词、错误码、产品名 | 不懂同义表达 |

两路召回后合并，能兼顾“意思像”和“字面准”。

**rerank：** 先粗召回较多候选，再用交叉编码器或业务规则精排。它比单纯向量相似度更懂 query 和文档之间的关系，但更慢，所以只对少量候选做。

**工程上还要做：** 去重、按用户和文档权限过滤、限制上下文 token、保留来源引用，并用固定问题集评估召回率和回答质量。

## Part 2 · 项目落地

### Q. MyLotion 现在怎么做上下文压缩？如果继续做长期记忆和 RAG，你会怎么接？

**参考答案（口述）**

**现在做的是短期记忆压缩：** 保留系统提示、最近若干轮消息和当前文档；更早的对话压成摘要，摘要里保留用户目标、约束、已确认事实和未完成事项。每次请求按 token 预算拼上下文，不能无限追加历史。

**为什么要串行化摘要更新：** 如果两个请求同时改写同一份摘要，后完成的旧结果可能覆盖新结果。做法是给同一会话加锁或串行队列，并带版本号；只接受基于最新版本的摘要。

**长期记忆的扩展方式：**

- 用户偏好、稳定事实放结构化表，带 `userId`、来源、更新时间和置信度；
- 大段笔记按文档和章节切 chunk，记录 `documentId`、`userId`、标题路径和版本；
- 每次问答先做权限过滤，再检索 top-k，必要时混合 BM25 和向量检索；
- 结果去重、重排、截断后拼进上下文，最终答案附文档引用。

**需要说清的边界：** 我当前项目已经落地的是滑动窗口 + 摘要；长期记忆和 RAG 是清晰的演进方案，不把“设计过”说成“已经上线”。面试时先讲现状，再讲为什么这样扩展。

## 30 秒复盘

短期记忆是当前会话里的最近消息和摘要，长期记忆是跨会话保存并可按相关性召回的信息。RAG 先从私有或最新资料中检索，再把相关 chunk 放进上下文生成答案；embedding 负责语义表示，向量相似度负责召回。chunk 要兼顾语义完整和 token 成本，overlap 防止边界截断；混合检索兼顾语义与精确词，rerank 对少量候选精排。MyLotion 当前用滑动窗口加摘要控制上下文，长期记忆和 RAG 可按“结构化事实 + 文档切片 + 权限过滤 + 混合检索”演进。
