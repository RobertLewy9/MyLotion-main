## 思维导图

```text
LLM 基础
├─ Token：计费、窗口、延迟的计量单位
├─ 上下文窗口：输入 + 输出共享预算
├─ 无状态：历史由应用存储并重新拼入
└─ 压缩：滑动窗口保最近原文 + 摘要保早期信息
```

## Part 1 · 概念

### Q1. Token 是什么？中文和英文大概怎么估？为什么工程上要关心？

**参考答案（口述）**

Token 是模型处理文本的基本单位，不严格等于一个汉字或一个英文单词。

**工程粗估：**

- 中文：**1 个字约 1 个 token**，保守估；
- 英文：**4 个字符约 1 个 token**；
- 再给系统提示词和输出预留约 **20%**。

关心它有三个原因：计费按 token、上下文窗口按 token、延迟和成本也随 token 增长。

面试不需要背精确 tokenizer；说清“粗估 + 留余量 + 必要时用 tokenizer 校验”即可。

### Q2. 上下文窗口是什么？输入和输出共享额度吗？超了会怎样？

**参考答案（口述）**

上下文窗口是一次请求里模型能看见的 token 上限，通常**输入和输出共享**这个额度。

超过上限时，可能直接报错，也可能被服务端截断。工程上不能等超限再处理，而要在组装 messages 时按预算压缩。

### Q3. 为什么说模型本身是无状态的？多轮对话怎么实现？

**参考答案（口述）**

模型不会自己保存上一轮会话；每次请求都要由应用重新提供历史。

所谓多轮对话，本质是：

1. 数据库保存历史消息；
2. 下一次请求取出需要的历史；
3. 重新组装成 `system + 历史/摘要 + 当前输入`；
4. 再把完整 Context 发给模型。

**一句话：** 模型负责推理，记忆由应用层实现。

### Q4. 上下文很长时怎么压缩？会丢什么？

**参考答案（口述）**

最直接的是**滑动窗口 + 摘要**：保留最近一段原文，更早的消息压成摘要。

代价是会丢失具体措辞、细节数字和早期约定。因此：

- 系统提示词不进入摘要；
- 用户偏好、权限、关键业务约束最好结构化保存；
- 最近原文优先保留，保证当前任务能接上。

## Part 2 · 项目落地

### Q. MyLotion 每次调用 Agent 时，发给模型的上下文由哪几部分组成？为什么不是无限拼历史？

**参考答案（口述）**

```text
系统提示词 + 历史摘要 + 最近 100 条未压缩原文 + 当前用户输入
```

这样设计有四个原因：

1. 最近内容保真，当前问题能接上；
2. 更早内容只留摘要，控制 token 成本和延迟；
3. 窗口大小固定，token 预算可预估；
4. 系统提示词永远不进摘要，避免角色设定和工具约束被压掉。

**一句话：** 模型无状态，记忆靠应用拼；压缩是在用细节换预算。

## 30 秒复盘

Token 是计费和窗口的计量单位，中文可按一字一 token、英文四字符一 token 粗估，并留 20% 余量。上下文窗口通常由输入和输出共享，超限会报错或截断。模型无状态，多轮对话靠应用重新拼历史。上下文过长时用滑动窗口 + 摘要，保留最近原文和系统提示词，接受早期细节的损失。
