## 1. Token 是什么、怎么估？

**一句话**：Token 是模型处理文本的基本单位，不严格等于一个汉字或一个英文单词。

工程上粗估：
- 中文按 **1 个字约 1 个 token** 保守估；
- 英文按 **4 个字符约 1 个 token** 估；
- 再给系统提示词和输出留约 **20%** 余量。

为什么关心：计费按 token、上下文窗口按 token、延迟和成本也随 token 增长。
面试不需要背某个模型精确的 tokenizer，说清“粗估 + 留余量 + 必要时用 tokenizer”即可。

## 2. 上下文窗口是什么？

**一句话**：一次请求里模型能看见的 token 上限，通常输入和输出共享这个额度。

超了可能报错，也可能被服务端截断。工程上不能等超了再处理，要在组装 messages 时按预算压缩。

## 3. 模型为什么无状态？多轮对话怎么实现？

模型不会自己记住上一轮；每次请求都要由应用把历史消息重新拼进去。
所谓“多轮对话”，本质是数据库存历史，下一次请求再组装成 `system + 历史 + 当前输入` 发给模型。

## 4. 上下文太长怎么压？

最直接的做法是**滑动窗口 + 摘要**：保留最近一段原文，更早的消息压成摘要。
代价是会丢失具体措辞、细节数字、早期约定；所以系统提示词不进摘要，关键用户偏好最好结构化保存。

## Part 2 · MyLotion 的上下文

```text
系统提示词 + 历史摘要 + 最近 100 条未压缩原文 + 当前用户输入
```

这样做的原因：
1. 最近内容保真，保证当前问题能接上；
2. 更早内容只留摘要，控制 token 成本和延迟；
3. 窗口大小固定，token 预算可预估；
4. 系统提示词永远不进入摘要，避免工具约束和角色设定被压掉。

一句话总结：**模型是无状态的，记忆是应用层拼出来的；压缩是用细节换预算。**
