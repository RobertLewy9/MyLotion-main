## 一、两分钟总述（面试官：「介绍一下你这个项目」）

> 这一段的节奏：**一句话定位 → 三层各一段 → 一个「最关键的」收尾**。别从头到尾平铺，最后那句是全场的钩子。

「我做的是一个 AI 笔记应用，核心是**让 AI 能直接操作笔记本身**，而不是只在对话框里回答问题。整体分三层：前端、API 加 Agent、数据层。

**前端**是 Next.js 15 的 App Router。界面三个区域：左边侧边栏是文档树，中间是 BlockNote 富文本编辑器，右边是 AI 面板。侧边栏和编辑器这一路**不经过我自己的后端**，直接用 Supabase 客户端读写数据库；但它是受 **RLS，也就是行级安全策略**保护的，用户只能读到自己名下的数据。AI 面板走另一条路，把消息 POST 到我写的 Route Handler —— 就是 Next.js 里放接口的地方。

**中间层是 API 加 Agent。** Route Handler 先做鉴权，确认当前用户是谁；再校验这个会话确实属于这个人，防止别人拿我的 sessionId 越权；然后做**幂等**落库 —— 前端每条消息带一个 requestId，数据库上有唯一约束，用户手抖点两次，第二次直接撞约束返回 409，不会多出一条消息。接着拉这个会话**最近一百条还没被压缩的历史**，加上之前的摘要，组装成 messages 交给 `streamText`。模型在这一层自己决定调哪个工具，我一共给了七个：搜索、读取、新建、更新、重命名、归档、删除，**全部在服务端执行**。

**数据层就一张 `documents` 表**，用 `parentDocument` 字段指向自己来实现无限层级，所以整棵树就是一张表，拉回来在内存里建树。安全不是靠前端过滤，而是落在数据库的 RLS 上 —— 前端那层只是体验，不是安全边界。

整条链路里最关键的一点是：**工具在服务端改数据，前端根本看不见它改了什么。** 所以我没有让前端轮询，而是给工具注入了 `onEvent` 回调，工具一改完就把事件上报出来，通过 **SSE**（服务端单向往前端推的 HTTP 长连接）推给前端，前端按事件类型刷新列表、显示进度、或者弹确认框。删除这类危险操作，模型**只能发起、不能执行**，必须用户确认之后前端才真的删。」

> 收尾这句「模型只能发起、用户才能执行」，是面试官最容易接话的地方 —— 他会顺着问「那怎么防止重复删除 / 怎么保证幂等」。

## 二、八步链路（面试官：「具体走一遍，一次请求怎么落地的」）

> 口诀：**发 → 验 → 拉 → 装 → 想 → 做 → 推 → 收**。
> 口述时每步都用「谁在动 + 干了什么 + 为什么这么干」三段式，别只报菜名。

**第一步，发。** 用户在 AI 面板敲一句话点发送，前端把消息内容、`sessionId`、还有一个 `requestId` 一起 POST 到 `/api/ai/chat`。`requestId` 是为幂等准备的，一会儿要撞数据库的唯一约束。

**第二步，验。** 服务端先调 `getUser` 拿当前用户，没登录直接 401；再确认这个 `sessionId` 属于这个人，防止拿别人的会话 id 越权；然后把用户这条消息落库。落库的时候 `requestId` 撞了唯一约束就返回 409 —— 这就是**幂等：同一个请求发多次，效果和发一次一样**。如果是这个会话的第一条消息，顺手用它的内容给会话起个标题。

**第三步，拉。** 拉上下文：这个会话里最近一百条**还没被压缩**的消息，加上已有的摘要。注意是「未被压缩」的，已经被摘要覆盖的那些不再原文带进去，否则等于重复计费。

**第四步，装。** 组装成 messages：系统提示词、历史摘要、最近一百条原文、当前输入。这里有个设计取舍 —— **窗口大小是写死的，不让模型自己挑**，这样每次请求的 token 上限是确定的、可预算的；模型的职责只是把滑出窗口的内容总结成摘要。

**第五步，想。** 调 `streamText`，把 model、七个 tools、还有 `stopWhen` 一起传进去。`stopWhen` 是**工具调用的步数上限**，比如五步，防止模型来回调工具停不下来 —— Agent 循环必须有刹车。

**第六步，做。** 模型先调搜索工具，服务端用 `ILIKE` 做标题模糊匹配，返回 id、标题和摘要；模型看到结果，决定调归档，服务端真正把数据改掉。这里要强调一句：**模型输出的是「我要调哪个工具、参数是什么」，真正的执行在后端**，模型从来没有直接碰数据库的权限。

**第七步，推。** 改完之后，工具通过注入的 `onEvent` 上报一个 `note_modified` 事件，事件先进队列；SSE 那一层每 200 毫秒把队列取出来，编码成 `data: <json>` 加两个换行的格式推给前端；前端按两个换行切分、`JSON.parse` 之后按 `type` 分发 —— 刷新列表、显示进度、或者弹确认框。文本的增量走另一类 `text` 事件。

**第八步，收。** 流结束后，后台把 assistant 这条消息连同 token 统计落库，再触发一次压缩检查：如果未压缩的消息超过阈值，就把滑出窗口的那批总结进摘要。压缩失败的话降级为「本轮不压缩」，不能因为压缩把这次对话搞挂。」

> 如果面试官只给你 30 秒，就讲 1、2、5、6、7 这五步 —— 请求进来、验身份、模型决策、服务端执行、事件推回前端。其余是细节。

## 三、三个必被追问的问题（背答法，不背句子）

**Q1：工具是在前端跑还是服务端跑？前端怎么知道数据变了？**

「服务端。工具定义在 `lib/ai/tools` 下，由 Agent 层注入给模型，模型只是决定调哪个。前端完全看不到工具内部执行，所以靠工具里的 `onEvent` 回调把副作用上报成显式事件，再经 SSE 推过去；前端按事件类型分发 —— 该刷新列表的刷新列表，该弹确认框的弹确认框。」

**Q2：为什么不让前端轮询？**

「轮询只能知道『变了』，不知道『变了几次、变的是哪一类』，而且多个工具同时写一个共享对象会有顺序耦合，谁先谁后说不清。事件回调把副作用变成**可枚举的事件类型**，新增一类副作用只要加一个事件，不会漏推；前端也能据此做不同的 UI 反应，而不是无脑重拉。」

**Q3：用户手抖点两次发送会怎样？**

「两次带的是同一个 `requestId`，第二次落库时撞唯一约束，直接返回 409，前端忽略就行。幂等键放在服务端、由数据库约束兜底，比前端加个 loading 禁用按钮可靠 —— 因为前端拦不住的场景（重试、多标签页、网络重发）它都能拦。」

> 附加题：**用户 @ 了一篇笔记，模型怎么知道是哪篇？**
> 「前端把胶囊序列化成 `[@标题](id)` 这样的纯文本，跟着 prompt 一起发过去；系统提示词里约定，看到这个标记就按 id 调读取工具。**服务端不解析这段文本** —— 解析规则容易和模型的理解打架，不如把 id 直接交给模型，让它自己取。」

## 四、三条「为什么不用 X」（面试官最爱在这里下刀）

**① 为什么用 SSE，不用 WebSocket？**
「我的场景是**单向**的：服务端往前端推 token 和事件，前端不需要在同一条连接上往回发。SSE 基于普通 HTTP，不用协议升级，浏览器自带重连，代理和负载均衡也友好。如果要做**双向**的实时协同编辑，我会换 WebSocket，或者协同那块单独走 WebSocket、AI 流式继续走 SSE。」

**② 为什么单表自引用，不用闭包表 / 路径枚举？**
「层级简单、查询少，一次把全量拉回来在内存里建树是 O(n)，比递归查库的 N+1 好得多。闭包表和路径枚举是为『按子树查、按深度查、层级极深』准备的，我现在的量级用不上 —— 真到那个量级，我再把 `parentDocument` 迁成闭包表，读多写少的场景收益更明显。」

**③ 为什么危险操作要做确认闸门？**
「因为模型的输出不可信。删除工具被调用时我不真删，只上报一个 `confirm_delete` 事件，前端弹框，用户点了确认才真的调 `remove()`。原则是**AI 只能发起，用户才能执行**；再叠一层 RLS 和 userId 过滤，保证它就算发起也越不了权。」

## 五、术语口述对照表（要说得出口，别现场卡壳）

| 术语 | 口述时怎么说（一句话，别背定义） |
|------|-----------------------------------|
| Route Handler | Next.js 里写 HTTP 接口的地方，相当于我自己搭的后端路由 |
| 鉴权 | 确认「你是谁」；授权是确认「你能不能碰这条数据」，我这两步都做了 |
| 幂等 | 同一个请求发多次，效果和发一次一样 |
| `requestId` + 唯一约束 | 幂等键落在数据库上，重复请求直接 409，不靠前端禁用按钮 |
| RLS（行级安全） | 安全策略写在数据库里，每条查询自动带上「只能看自己的」，前端绕不过去 |
| 副作用 | 工具执行时对数据的实际改动，比如改了或删了某条笔记 |
| `onEvent` | 工具把副作用上报成显式事件的回调，前端靠它知道发生了什么 |
| `eventQueue` | 事件先排队，SSE 层定时取，避免工具执行和网络推送耦合 |
| SSE | 服务端单向推的 HTTP 长连接，消息格式是 `data: <json>` 加空行 |
| `stopWhen` | Agent 循环的步数上限，防止模型反复调工具停不下来 |
| 上下文窗口 | 一次请求能塞给模型的 token 上限，超了就得裁 |
| 滑动窗口 + 摘要 | 最近 N 条保留原文，更早的压成摘要，兼顾成本和记忆 |
| Tool / Function Calling | 给模型一份函数清单，模型输出「调哪个、参数是什么」，执行在服务端 |
| Tool schema | 工具的名字、描述、参数结构，模型靠它判断该不该调 |

## 六、30 秒电梯版（自我介绍里带一句）

「我做过一个全栈 AI 笔记应用，核心是让模型通过工具直接增删改查笔记。前端 Next.js 加 BlockNote，数据用 Supabase 的 Postgres 加 RLS，AI 这块用 Vercel AI SDK 驱动 Agent 循环，一共七个工具、全部在服务端执行；工具产生的副作用通过事件回调走 SSE 推给前端。比较有意思的是删除这类危险操作，我做成了模型只能发起、用户确认才执行。」
