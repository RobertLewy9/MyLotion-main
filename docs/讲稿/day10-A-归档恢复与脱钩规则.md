# Day 10 · A 轨 —— 归档 / 恢复：递归转 O(n) 批量与脱钩规则

> **归属：Day 10 · A 轨（MyLotion）**
> 日期：2026-11-11
> 代码：`src/data/archive.ts`；用例：`test/data/archive.test.ts`（8 个）。
> 目标：把“每层递归查子节点”改成一次内存遍历 + 一次批量更新，并讲清恢复时父链不可见怎么办。

## 一、一句话（10 秒）

> 先按用户把整棵树扁平拉回，在内存里 O(n) 算出“根 + 全部后代”，再拿 id 列表做一次批量更新；恢复时如果父节点或祖先不可见，就把子树的根挂到顶层，子树内部关系保持不变。

## 二、开场胜：先接上 Day 9

Day 9 的 `DocumentCache` 解决的是**读取链路**：并发去重、LRU、`invalidate`、`fresh`、`prefetch`。

今天处理**写入链路**：归档或恢复一个节点时，整棵子树都要跟着变。它和缓存的关系是：

```text
归档 / 恢复成功
  → 后端批量更新 is_archived
  → 前端让受影响的文档缓存失效
  → 侧边栏重新取数或做一致性更新
```

## 三、问题：递归实现为什么慢

典型写法是：

```ts
async function archive(userId: string, id: string) {
  await update(id, { isArchived: true });
  const children = await selectChildren(userId, id);
  for (const child of children) {
    await archive(userId, child.id);
  }
}
```

一棵 100 个节点、5 层深的树，会产生大量网络往返：

- 每层查一次子节点，典型的 N+1；
- 每个节点再发一次更新；
- 中途失败会留下“父节点已归档、部分子节点没归档”的半截状态；
- 恢复同理，还可能把一棵子树拆散。

## 四、思维导图

```text
归档 / 恢复
├─ 输入：同一用户的全部文档行（扁平数组）
├─ 建索引：id → row，parentDocument → children
├─ 求集合：根 + 全部后代（BFS，防环）
├─ 归档
│  ├─ 整棵子树 is_archived = true
│  ├─ 不修改 parentDocument，保留树形
│  └─ 一次 in 批量更新
├─ 恢复
│  ├─ 整棵子树 is_archived = false
│  ├─ 父链可见：保留原 parentDocument
│  └─ 父链不可见：子树根 parentDocument = null（脱钩）
└─ 收尾：事务 + 权限过滤 + 缓存失效
```

## 五、O(n) 的计算步骤

`planArchiveRestore()` 做四件事：

1. `byId`：一次扫描，建立 `id → row`；
2. `childrenByParent`：一次扫描，建立父 id 到直接子节点的索引；
3. 从 `rootId` 开始 BFS，把根和全部后代放进 `ids`；
4. 归档直接返回计划；恢复时再检查父链是否可见，决定是否脱钩。

代码里的 `ids` 顺序是 BFS：先根，再第一层，再第二层。这个顺序便于讲清父子关系，但数据库批量更新不依赖顺序。

**复杂度：**

- 时间：建索引 O(n) + 遍历子树 O(n) = **O(n)**；
- 空间：索引、队列、结果集合都是 **O(n)**；
- 网络：从 O(节点数) 次往返降到 **O(1) 次批量更新**。

## 六、归档规则

### 1. 归档根节点，就归档整棵子树

父节点被归档后，子节点即使自己没变，也不应该继续出现在正常侧边栏里。所以 `ids` 必须包含根和全部后代。

### 2. 归档不修改 `parentDocument`

这是软删除，不是把节点从树里永久摘掉。保留原来的父子关系，恢复时才能还原结构。

如果归档时把 `parentDocument` 清空，就相当于把每个节点都“脱钩”到顶层；恢复后树形全丢了。

### 3. 批量更新而不是逐条更新

伪代码：

```sql
update documents
set is_archived = true
where user_id = :userId
  and id in (:ids);
```

真实项目里应放在事务或 RPC 中，保证“全成功或全失败”。

## 七、恢复规则与“脱钩”

恢复时要把整棵子树设回 `is_archived = false`，但根节点还要处理父链。

| 根节点原来的父链 | 处理 |
|---|---|
| 父节点存在且所有祖先都未归档 | 保留 `parentDocument`，回到原位 |
| 父节点已归档 | 根节点 `parentDocument = null`，提升到顶层 |
| 某个祖先已归档 | 同上，避免恢复后仍然不可见 |
| 父节点缺失 | 同上，避免成为孤儿 |
| 父链成环 | 同上，并靠 `visited` / `seen` 防死循环 |

### 为什么只改“子树的根”

恢复的目标是让这棵子树重新可见。根节点换到顶层后，它的子节点仍然挂在它下面，整棵树的结构就保住了。

如果连子节点也逐个改父指针，会把内部结构打散，既多写数据又难恢复。

### “脱钩”不是“删除”

```text
脱钩：parentDocument = null，文档还在，只是提升为顶层
删除：物理删除记录，或走单独的硬删除流程
```

这两个概念面试时不能说混。

## 八、完整执行顺序

```text
用户点击归档 / 恢复
  → 校验 userId 与权限
  → 拉取当前用户文档行
  → planArchiveRestore(rows, rootId, action)
  → 一次批量更新 ids
  → 恢复脱钩时额外更新根的 parentDocument
  → 让受影响 id 的缓存失效
  → 重新取侧边栏 / 做乐观更新
```

前端可以用 `applyArchivePlan()` 做乐观更新；它返回新数组，不修改入参，适合配合 React 状态更新。

## 九、边界与一致性

- **权限**：所有查询都必须带 `userId`，数据库再用 RLS 兜底，不能只信前端传的 id。
- **事务**：根节点的父指针更新和整棵子树的 `is_archived` 更新应在同一事务里。
- **并发**：同一棵树被两个标签页同时操作时，以服务端结果为准；可用 `updatedAt` 或版本号拒绝乱序覆盖。
- **缓存**：归档 / 恢复影响多个 id，不能只失效根节点；至少要失效 `plan.ids`，或直接让侧边栏缓存整体失效。
- **数据损坏**：父子成环、父节点缺失时不能死循环；找不到父节点就按顶层处理。
- **大子树**：`in` 列表过长时按批次切分，但批次要放在事务里；更大规模应改为数据库递归 CTE 或闭包表。

## 十、2 分钟口述版

> 归档和恢复如果按层递归查子节点，会产生 N+1 查询，节点一多就很慢，而且中途失败会留下半截状态。我的做法是先把当前用户的文档行一次拉回，建立 id 索引和 parentDocument 到 children 的索引，再从根节点 BFS 一次算出根和全部后代，最后用这组 id 做一次批量 update。归档只改 is_archived，不删除也不清空 parentDocument，这样树形还在，恢复时能还原。恢复时我会检查父链：如果父节点和所有祖先都可见，就保留原位置；如果父节点或祖先已经归档、缺失或成环，就把这个子树的根 parentDocument 设为 null，提升到顶层，子树内部关系不动。整个操作带 userId 和 RLS，放在事务里，最后让受影响文档的缓存失效。

## 十一、追问预判

### 为什么不用递归 CTE？

递归 CTE 也能在数据库里算出子树，但当前项目已经把侧边栏当扁平数组拉回内存，复用现成数据更简单，前端和测试也更容易做纯函数验证。数据量再大、不能整树加载时，再考虑递归 CTE 或闭包表。

### 为什么不在数据库里 `on delete cascade`？

归档是软删除，记录还要保留；`on delete cascade` 是物理删除语义，不能拿来替代归档。

### 恢复时为什么不自动恢复所有祖先？

自动恢复祖先会把用户没有明确选择的父节点也一起恢复，副作用更大。更可控的做法是只恢复当前子树，父链不可见就脱钩到顶层。

### 这个方案和 Day 2 的 `collectSubtreeIds` 什么关系？

Day 2 算“全部后代”，今天要在它基础上把根节点也纳入，并增加归档 / 恢复语义和脱钩判断。核心索引和遍历方式一致。
