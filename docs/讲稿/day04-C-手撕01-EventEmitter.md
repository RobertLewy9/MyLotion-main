# Day 4 · C 轨 —— 手撕 01：EventEmitter（on / once / off / emit）

> **归属：Day 4 · C 轨（力扣 / 手撕）**
> 来源：IEG 一面编程题。
> 实现：`src/interview/event-emitter.ts`；用例：`test/interview/event-emitter.test.ts`（12/12 ✅）。

## 1. 一句话

一张「事件名 → 监听器数组」的登记表：`on` 往里塞函数，`emit` 拿着事件名把里面的函数挨个调一遍。

## 2. 它解决什么问题

支付成功后要发短信、加积分、写日志。最土的写法是把三件事硬编码进支付函数：

```ts
function paySuccess(order) {
  sendSms(order);
  addPoints(order);
  writeLog(order); // 每来一个新需求，都得回来改这个函数
}
```

换成事件总线，支付模块只认识 `"order:paid"` 这个名字，不认识短信 / 积分 / 日志：

```ts
const bus = new EventEmitter();

bus.on("order:paid", (order) => sendSms(order));
bus.on("order:paid", (order) => addPoints(order));
bus.on("order:paid", (order) => writeLog(order));

bus.emit("order:paid", order); // 支付模块只喊这一声
```

想再加「发优惠券」，外面 `bus.on` 一下就行，支付函数一行不改。
这就是发布-订阅：**发布方和订阅方互不认识，只认事件名**。
Node 的 `EventEmitter`、浏览器的 `addEventListener`、Vue 的 `$emit`，都是这一套。

## 3. 数据结构

```ts
private readonly events = new Map<string, Listener[]>();
//                    事件名 ↓    ↑ 同一事件的多个监听器，按注册顺序排列
```

用 `Map` 而不是普通对象，是为了避开 `obj["__proto__"]`、`obj["constructor"]` 这类键名踩到原型链的坑。

## 4. 四个方法

| 方法 | 做什么 | 复杂度 |
|------|--------|--------|
| `on(event, fn)` | 追加到数组末尾 | O(1) |
| `once(event, fn)` | 包一层 wrapper，触发一次后自动移除 | O(1) |
| `off(event, fn)` | 按原函数过滤移除；事件或函数不存在时静默返回 | O(k) |
| `emit(event, ...args)` | 遍历快照逐个调用，参数原样透传 | O(k) |

k = 该事件当前的监听器数量。

## 5. 三个追问点（这份实现真正的难点）

### 5.1 `once` 为什么要包一层 wrapper

存进数组的不是原函数 `fn`，而是包装函数：

```ts
const wrapper = ((...args: unknown[]) => {
  this.off(event, fn); // ① 先把自己从登记表里摘掉
  fn(...args);         // ② 再执行原函数
}) as OnceWrapper;
wrapper.listener = fn; // ③ 留个记号，指回原函数
this.on(event, wrapper);
```

**① 必须排在 ② 前面。** 反过来写（先跑再摘），原函数里若再 `emit` 同一个事件就会递归重入。
实测：注册一个「每次都重新 `emit("tick")`」的 once 监听器，先摘后跑触发 **1** 次，
先跑再摘触发 **5** 次（本例里带了 `count < 5` 的刹车，否则直接栈溢出）。

> **自己跑一遍**（不改实现就能复现）：
>
> ```ts
> const ee = new EventEmitter();
> ee.once("message", () => {
>   console.log("收到消息");
>   ee.emit("message"); // 回调里再触发同一个事件
> });
> ee.emit("message");
> ```
>
> 现在的实现只打印 **1** 次；把 `off` 挪到 `fn` 后面，就会一直打印到栈溢出。

**③ 是为了能被 off 掉。** 用户写的是 `once("a", foo)`，登记表里存的却是 `wrapper`，
所以 `off("a", foo)` 用 `cb === fn` 比对根本找不到人。`off` 因此多一条判断：

```ts
const next = list.filter(
  (cb) => cb !== fn && !(isOnceWrapper(cb) && cb.listener === fn),
);
```

两个条件合起来 = 「直接 `on` 进去的按原函数删，`once` 包过的也按原函数删」——对齐 Node `removeListener` 的行为。

### 5.2 `emit` 为什么要 `[...list]` 快照

因为回调里可能 `on` / `off`，边遍历边改数组会让本轮遍历错乱。实测：

| 回调里干了什么 | 有快照 | 无快照 |
|----------------|--------|--------|
| `on` 一个新监听器 | 本轮**不触发**（0 次） | 本轮**就被触发**（1 次） |
| `off` 掉后面的监听器 | 后面的本轮仍触发 | 后面的本轮仍触发（同样 1 次） |
| `once` 触发时 `off` 自己 | 不受影响 | 不受影响 |

后两行两种写法结果一样，是因为这里的 `off` 用 `filter` + `set` 给 Map **重建了一个新数组**，
而不是原地 `splice` —— 正在被遍历的老数组压根没被动过。
也就是说：快照在这里主要防的是「**边遍历边新增**」；另外只要你哪天把 `off` 改成原地 `splice`，
无快照的实现就会漏掉后一个监听器。

> 面试里说满的一句：**遍历前先复制一份，保证「本轮触发哪些监听器」在开始时定死。**
> 这是本轮语义的定义问题，不只是防 bug。

### 5.3 `off` 里为什么要 `delete` 空数组

不留空壳是防 `Map` 无限增长。实测：注册再注销 1000 个不同事件名（`e0`…`e999`），
带 `delete` 的 `Map.size` 是 **0**，不带的是 **1000**。

注意泄漏的只是 **key + 空数组壳子**，回调函数本身已经不在数组里、可以被 GC。
所以这是「慢性增长」而不是「回调泄漏」；但像 `user:12345` 这种按 id 动态拼出来的事件名，量一大就很明显。

## 6. 用例对照

| 用例 | 守住的规则 |
|------|------------|
| on + emit / 参数透传 / 多个监听器按序触发 | 基本订阅与注册顺序 |
| emit 一个没有监听器的事件不报错 | 静默返回 |
| off 按原函数移除 / 事件或函数不存在静默返回 | `off` 的两条兜底 |
| once 只触发一次 / 参数透传 | wrapper 的「触发即摘」 |
| once 注册的监听器能被原函数 off 掉 | `wrapper.listener` 反查 |
| emit 过程中移除监听器不影响本轮 | 快照语义（off 场景） |
| emit 过程中新增监听器本轮不触发 | 快照语义（on 场景） |
| once 原函数里重新 emit 不会重入 | 「先摘再跑」的顺序 |

> 最后两条是补的：把 `[...list]` 去掉、或把 `off` 挪到 `fn` 之后，
> 原来的 10 条用例**全都照样绿**——坑是真实存在的，用例没盖住而已。

## 7. 追问预判

- Q：某个监听器抛异常会怎样？
  A：会中断后续监听器，并把异常抛给 `emit` 的调用方。要做到「互不影响」得在循环里 try/catch。
- Q：同一个函数被 `on` 两次，`off` 一次会删几个？
  A：现在的实现一次全删（`filter` 过滤掉所有匹配项）。Node 是一次只删最近注册的那一个 —— 这是个可以主动提的差异点。
- Q：`on` 返回 `this` 有什么用？
  A：链式调用 `ee.on("a", f).on("b", g)`。
- Q：参数类型为什么用 `unknown[]` 而不是 `any[]`？
  A：`unknown` 逼着使用前收窄类型，比 `any` 安全；这题不要求泛型事件表，可读性优先。
- Q：为什么 `events` 用 `Map` 不用普通对象？
  A：避开 `__proto__` 这类键名污染，也不用每次 `Object.keys` 遍历。

## 8. 我的作答与订正（Day 4 自查）

> 三个结论都跑过实验：把实现改坏、重跑用例，看谁挂谁不挂。

### Q1：去掉 `emit` 里的快照，12 条里有几条会挂？

- 我原答：最后 4 条会挂，因为遍历过程中有人增删改原监听器数组。
- **订正：只挂 1 条** —— 「emit 过程中新增监听器，本轮不触发」。
- 关键在「**原地改** vs **重建数组**」这个分水岭，不是「增删改」三个字。
- `off` 在这份实现里是 `filter` + `set`，**给 Map 换了一个新数组**，正在被遍历的老数组压根没被动过 —— 所以「emit 过程中移除监听器」那条照样绿。
- `once` 触发时 `off` 自己，同理不受影响。
- 真正会咬人的只有 `on`：它是原地 `push`，改的正是正在遍历的那个数组对象。

### Q2：把 `once` 的 `off` 挪到 `fn(...args)` 之后会怎样？

- 我原答：会重复递归调用引发栈溢出。→ 对。
- 补充（这问的后半截没答）：**原来那 10 条为什么发现不了** —— 它们只在**外面**连喊三次 `emit`，
  而外部连续 emit 时，无论先摘还是后摘，第一轮结束都已经把自己摘掉了，第二轮起就没人响应，次数都是 1。
  必须让**回调内部再 emit 同一事件**（重入）才暴露差异，原来缺的正是这个场景。

### Q3：`off` 里不 `delete` 空数组会怎样？

- 我原答：功能上不出错，代价是空数组沉积、占额外内存。→ 对。
- 补充：泄漏的是 **key + 空数组壳子**，回调函数本身已被移出数组、能被 GC 回收 ——
  所以不是「泄漏回调」，是「登记表慢性变长」。危险程度取决于**不同事件名的数量**：
  固定那几个事件名无所谓，`user:12345` 这种按 id 动态拼出来的才是隐患。
