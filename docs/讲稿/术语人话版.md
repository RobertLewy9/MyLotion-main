# 术语人话版 —— 面试口述专用

> **用法**：面试时说三句，不是一句 ——「**人话（解决什么问题）→ 术语（它叫什么）→ 取舍（为什么不用 X）**」。
>
> 反例（背书，不加分）：「SSE 是一种基于 HTTP 的服务器推送技术。」
> 正例（人话，加分）：「服务器要把结果一条条推给浏览器，但不需要浏览器回话，所以用 SSE 就够了 ——
> 它就是普通 HTTP 上的一条长连接，浏览器不用装额外协议。」
>
> 判断标准只有一条：**对面没做过这个项目，能不能听懂你在说什么。**

## 1. 全人话版（一个术语都不带，先练这个）

> 目标：一口气讲完 60 秒，中间不停。讲得下来，说明你是真懂，不是背的。

「这个应用分三块。

第一块是用户直接看到的东西：左边是文件夹树，中间是写笔记的编辑器，右边是跟 AI 聊天的面板。

第二块是后台。用户点发送之后，后台先确认他是谁、这条消息是不是手抖重复发的；
确认没问题，再把之前聊过的记录捞出来，跟这次说的话一起打包交给 AI。
AI 想干活的时候，不是自己动手，而是从我们给它的几个按钮里挑一个 ——
搜笔记、读笔记、建笔记、改笔记、改名、归档、删除，一共七个。
真正按按钮的是后台代码，AI 只负责说要按哪个。

第三块是仓库。所有笔记都放在**一张表**里，每条笔记自己记着「我爸是谁」，
所以能一层层往下套，想多深有多深；仓库自己还有门禁，不是你的笔记，它压根不会拿出来。

中间有个最容易漏的点：后台按了按钮、把数据改了，右边那个聊天面板是**看不见**的。
所以每次改完，后台要主动喊一声「我改了哪一篇」，前端听到之后再去刷新列表 ——
这就是为什么要有事件上报，而不是让前端傻等或者一直问。」

## 2. 正式版（人话 + 术语，面试真正要说的）

> 在上一版的基础上，把该报的名字报出来。顺序还是：先说事，再报词。

「Lotion 是个全栈 AI 笔记应用，分三层。

**前端**三个区域：侧边栏树、BlockNote 编辑器、AI 面板。前两个用 `supabase-js` 直连数据库，
受 RLS 管；第三个把输入 `POST /api/ai/chat`，带 `sessionId` 和幂等用的 `requestId`。

**API + Agent 层**：`route.ts` 先鉴权、校验会话归属、用 `requestId` 做幂等，
然后拉最近 100 条未压缩历史加摘要，组装成 `messages` 交给 `streamText`；
模型自己决定调哪个工具，7 个工具**都在服务端执行**。

**数据层**：一张 `documents` 表，`parentDocument` 自引用做无限层级，配 RLS 兜底。

关键的一条线是：工具在服务端改了数据，前端看不见 ——
所以工具内部用注入的 `onEvent` 上报副作用，事件进 `eventQueue`，
SSE 层每 200ms 把队列编码成 `data: <json>\n\n` 推给前端，前端按 `type` 分发，
该刷新列表的刷新列表，该弹确认框的弹确认框。」

## 3. 八步：人话 ↔ 术语 对照

| # | 人话版（先这么说） | 然后报术语 |
|---|-------------------|-----------|
| 1 发 | 用户在右边输入框敲一句话，点发送 | `POST /api/ai/chat`，带 `sessionId` + `requestId` |
| 2 验 | 后台先确认你是谁、这条是不是重复发的，没问题才存下来 | 鉴权 / 会话归属校验 / 幂等（撞唯一约束返回 409） |
| 3 拉 | 把这轮之前聊过的记录捞出来 | 最近 100 条**未压缩**历史 + 会话摘要 |
| 4 装 | 把「规矩 + 老记录 + 这次的话」打成一个大包给模型 | `messages` = `[系统提示词] + [摘要] + [最近 100 条] + [当前输入]` |
| 5 想 | 模型看完说「我得先搜一下」 | `streamText({ model, tools, stopWhen })` → 发起 tool call |
| 6 做 | 后台真的去搜、去归档 | 工具在服务端执行，模型只决定调哪个 |
| 7 推 | 后台改完主动喊一声，前端听到就刷新 | `onEvent` → `eventQueue` → SSE（`data: <json>\n\n`）→ 按 `type` 分发 |
| 8 收 | 这轮结束，把 AI 的回复存起来，顺手看看要不要压缩 | `done` → 落库 assistant 消息 → `maybeCompressSession` |

## 4. 术语对照表（面试直接用）

### 4.1 架构与数据

| 术语 | 一句话人话 | 面试时怎么说 |
|------|-----------|-------------|
| **三层架构** | 按「谁跟用户打交道 / 谁决定干什么 / 谁存东西」切成三块 | 「前端管界面，API+Agent 管编排，数据层管存和兜底安全」 |
| **Supabase（BaaS）** | 别人帮你搭好的后端：登录、数据库、权限都现成 | 「BaaS，托管了认证、Postgres、RLS 和实时订阅，我不用自己搭一套后端」 |
| **RLS（行级安全）** | 数据库在把每行数据交给你之前，先查「这行是不是你的」 | 「安全落在数据库层 —— 不是你的数据，SQL 查出来也是空的；前端过滤只是体验，不是安全」 |
| **anon key / service_role** | 一个是能发给浏览器的访客卡，一个是只能待在后端的万能钥匙 | 「`service_role` 绕过 RLS，所以只在服务端用，且每条查询都必须自己带 `userId` 过滤」 |
| **单表自引用** | 每条笔记里写一句「我爸爸是谁」，自己就长成一棵树 | 「一张 `documents` 表，`parentDocument` 指向同一张表的另一条，根节点是 `null`」 |
| **全量拉取 + 内存建树** | 不一层一层问数据库，一次全捞回来在内存里拼 | 「`getSidebarAll` 一次拉全量扁平数组，前端 `O(n)` 建树，避免 N 次网络往返」 |
| **懒加载** | 先给展开的那层，点开哪个再要哪个的孩子 | 「前端懒加载 + 后端按 `parentId` 按需返回，而不是一次拉全量子树」 |
| **N+1** | 拿到父节点后对每个孩子再查一次，层数一深查询就爆炸 | 「递归查子节点是典型的 N+1，我们改成一次全量拉取、内存建树，复杂度降到 O(n)」 |
| **邻接表 / 闭包表 / 路径枚举** | 存树的三种方式：只记爸爸 / 把祖孙关系全存一遍 / 把路径写成字符串 | 「邻接表写入轻、深层查询要递归；闭包表查子树快但写入重；路径枚举适合前缀范围查询」 |

### 4.2 API 与请求

| 术语 | 一句话人话 | 面试时怎么说 |
|------|-----------|-------------|
| **鉴权** | 先确认你是谁，没登录直接挡在门外 | 「`route.ts` 第一步 `supabase.auth.getUser()`，没登录返回 401」 |
| **会话归属校验** | 确认这个会话是你的，不是别人的 | 「校验 `sessionId + userId`，防止往别人的会话里塞消息」 |
| **幂等** | 同一件事做两遍，结果跟做一遍一样 | 「发送带 `requestId`，数据库加唯一约束，重复请求直接 409」 |
| **409** | 「这条我已经收过了」 | 「第二次落库撞唯一约束返回 409，前端静默忽略就行」 |
| **请求去重** | 同一篇文档同时来两次请求，第二次不重复发，直接等第一次 | 「`pendingById` 里存 promise，并发请求共用一个」 |
| **LRU 上限** | 缓存只留最近用的 200 条，超了扔最久没用的 | 「不设上限就是内存泄漏，所以 200 条封顶、LRU 淘汰」 |
| **未压缩历史** | 还没被摘要「吃掉」的那些原文 | 「只拉未压缩的最近 100 条 —— 已压缩的已经由摘要素代表了」 |

### 4.3 AI 与 Agent

| 术语 | 一句话人话 | 面试时怎么说 |
|------|-----------|-------------|
| **模型无状态** | 模型不记事，每轮都得把老对话重新递一遍 | 「模型本身无状态，多轮对话靠每次把历史重新拼进 `messages`」 |
| **上下文 / context** | 这一轮递给模型的「一整包材料」 | 「上下文 = 系统提示词 + 摘要 + 最近窗口 + 当前输入」 |
| **system prompt** | 事先写好的员工手册：你是谁、能干什么、不许干什么 | 「系统提示词定角色、能力和禁区，用户内容永远不能覆盖它」 |
| **滑动窗口** | 只带最近 100 条原文 | 「`WINDOW_SIZE = 100`，窗口外的只留摘要」 |
| **摘要压缩** | 把要挤出去的老对话，让模型改写成一段摘要 | 「重写式摘要：旧摘要 + 本次滑出的消息 → 新摘要；**先写摘要再标记**，避免标记了却没摘要」 |
| **确定性窗口** | 留哪几条是代码算的，不是让模型挑的 | 「窗口确定性，模型只负责总结；这样可复现，token 也能算」 |
| **Agent loop** | 想一步 → 调个工具 → 看结果 → 再想 | 「模型不是一次答完，而是循环几轮，每轮可以调一个工具」 |
| **stopWhen** | 最多让它想 5 步，防止绕圈 | 「`stopWhen: 5 步`，跑偏和死循环的兜底」 |
| **Tool Calling** | 不给模型数据库权限，只给它几个按钮 | 「7 个工具：search / read / create / update / rename / archive / delete」 |
| **工具 schema** | 按钮的说明书：叫什么、要哪些参数、什么类型 | 「每个工具定义 name / description / 参数 schema，模型按 schema 填参数」 |
| **工具在服务端执行** | 模型只说要按哪个，真正按的是我们的代码 | 「模型只决定调哪个工具，执行、鉴权、超时都在服务端」 |
| **onEvent** | 工具改完数据，主动喊一声「我改了什么」 | 「工具内部经注入的 `onEvent` 上报 `note_modified`，不靠前端猜」 |
| **eventQueue** | 喊话先排队，攒一批再统一发 | 「事件进 `eventQueue`，SSE 层每 200ms 取一次」 |
| **SSE** | 服务器单向、一条条往浏览器推，用的还是普通 HTTP | 「单向推送够用、无需协议升级、自动重连、代理友好；要双向协同才换 WebSocket」 |
| **200ms 取队列** | 不是轮询数据库，是隔 200ms 把队列里的事件打包发出去 | 「200ms 是发送节流，不是前端轮询数据库 —— 数据变化是推的，不是拉的」 |
| **确认闸门** | 删除这种危险动作，模型只能说「我想删」，用户点确认才真删 | 「AI 只能发起，用户才能执行 —— 模型永远没有直接删除权限」 |
| **withToolLogging** | 每个工具外面套一层统一的壳：错误翻成人话 + 30 秒超时 | 「异常转成可读字符串回给模型，让它自己重试；每个工具 30s 显式超时防挂起」 |
| **背压 / abort** | 下游处理不过来、或者用户点了取消，要能掐断上游生成 | 「流式必须能中断，否则用户关了页面 token 还在烧」 |

## 5. 三个万能句式（卡壳时救命）

1. **「你可以把它理解成……」** —— 把术语换成一个生活里的东西（快递、员工手册、门禁、按钮）
2. **「说白了就是……」** —— 把一句话翻译成大白话，再补术语名
3. **「它解决的是……的问题」** —— 先说痛点，再说方案，最后报名字（面试官最吃这一套）

## 6. 口述的三个坑

1. **一上来背定义** —— 「XX 是一种……」是背书；先说「为什么需要它」才是理解
2. **用术语解释术语** —— 「RLS 就是行级安全的策略」等于没说；要说「数据库帮你把别人的数据藏起来」
3. **只说是什么，不说取舍** —— 面试官真正在听的是「为什么不用另一个」，每讲一个词，留一句给取舍

## 7. 禁忌对照：有些说法一听就是小儿科

> 判断标准：**把术语删掉，这句话还成立吗？**
> 成立 = 你在讲人话（加分）；不成立 = 你在背名词（减分）。**两者都要有，顺序是先人话、后术语。**

| 别这么说 | 这么说（术语 + 口述感） |
|----------|------------------------|
| 「前端把数据发给后端」 | 「前端把输入、`sessionId` 和幂等键 `requestId` POST 到 Route Handler」 |
| 「后端处理一下」 | 「API 层做鉴权、会话归属校验、幂等落库和上下文组装」 |
| 「模型自己去数据库改」 | 「模型只产出 tool call，真正的写操作由服务端工具执行」 |
| 「页面刷新一下」 | 「前端按事件 `type` 做局部状态更新」 |
| 「存一下 / 存个记录」 | 「落库」 |
| 「防止重复」 | 「幂等键 + 数据库唯一约束兜底」 |
| 「模型记不住太多」 | 「上下文窗口有上限，超了要么截断要么报错」 |
| 「工具跑完告诉前端一声」 | 「工具通过注入的 `onEvent` 把副作用上报成显式事件」 |
| 「数据不存在一个地方」 | 「单表自引用，用 `parentDocument` 指向同表主键表达层级」 |

## 8. 追问模板：结论 → 怎么做 → 代价

面试官追问时，**别从背景讲起**，按这三段答，20 秒就能答完：

1. **结论** —— 一句话先给答案：「工具在服务端跑。」
2. **怎么做** —— 两句讲流程：「模型产出 tool call，服务端执行工具，执行完通过 `onEvent` 上报事件。」
3. **代价 / 边界** —— 一句讲取舍：「代价是前端不能直接复用工具函数，但换来了权限和校验都收在服务端。」

> 例：**为什么不用 WebSocket？**
> 「因为这里只有服务端到客户端的单向推送。」→「SSE 基于普通 HTTP，不需要协议升级，浏览器自带重连，代理也友好。」→
> 「代价是不能双向，所以真要做多人协同编辑，我会换 WebSocket，或者 SSE 收事件 + HTTP 发操作的组合。」
