# 示例：Day 1 扁平数组还原成文档树

> 这是一份**示范**，告诉你讲稿该长什么样、颗粒度多大。用你自己的话说，别照抄。

## 1. 一句话

把数据库一次性拉回来的扁平文档数组，在前端还原成无限层级的文档树。

## 2. 背景与痛点

侧边栏要展示文档的无限层级结构，但数据库里每个文档只存一个 `parentDocument` 指向父节点，
所以查出来是个**扁平数组**。如果每个节点都单独查一次子节点，就是经典的 N+1 查询；
如果在前端用递归 `filter` 去拼树，每个节点都要扫一遍全表，复杂度 O(n²)。

## 3. 方案

两遍扫描、O(n)：第一遍把所有文档塞进一个 `id → 节点` 的 `Map`，
同时给每个节点初始化空 `children`；第二遍按 `parentDocument` 把节点挂到父节点的 `children` 上，
`parentDocument` 为 `null` 的就是根。同级节点保持原数组顺序。

## 4. 替代方案与取舍

| 我选的 | 替代方案 | 为什么选前者 |
|--------|----------|--------------|
| 全量拉回 + 内存建树 O(n) | 每层单独查一次（懒加载查询） | 文档量不大时一次拉完更省往返；懒加载留给层级极深的场景 |
| 递归 `filter` 建树 | | O(n²)，节点一多就明显 |
| `id → 节点` 的 Map | 边遍历边建树（单遍） | 单遍需要父节点先于子节点出现，不能保证顺序；两遍更稳 |

## 5. 踩过的坑 / 边界

- **孤儿节点**：`parentDocument` 指向一个不存在的 id 时，不能让它凭空消失，我把它提升为根节点
- **纯函数**：不能修改传入的数组和对象（测试里专门有一条用例比对 `JSON.stringify`）
- **返回新对象**：不能直接复用传入对象引用，否则外部改动会串味

## 6. 追问预判

- Q：为什么不用数据库的递归 CTE 直接查树？
  A：可以，但侧边栏要的是**全部**文档，多次往返不如一次拉全量；而且前端还原树还能复用缓存。
- Q：层级特别深怎么办？
  A：渲染层做虚拟滚动 + 懒展开；数据层仍是 O(n)，不会随深度退化。
