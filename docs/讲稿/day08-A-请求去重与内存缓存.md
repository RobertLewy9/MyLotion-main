# Day 8 · A 轨 —— 文档详情：请求去重 + 内存缓存 + LRU 上限

> **归属：Day 8 · A 轨（MyLotion）**
> 2026-10-29 按 8 场面经校准：CSIG 一面手写 LRU；性能优化、并发请求是项目追问的常见入口。
> 今天只回答一个工程问题：**同一篇文档被多处同时读取时，怎样少发请求、又不把内存吃满？**
> 代码：`src/data/document-cache.ts`；用例：`test/data/document-cache.test.ts`。

## 一、一句话（10 秒）

「文档详情用 **pending Map 合并并发请求**，用 **cache Map 缓存成功结果**，
再用 **Map 的插入顺序做 LRU**，把常驻条目限制在 200 个；数据变更时主动失效。」

## 二、背景与痛点（20 秒）

详情页、侧边栏预取、AI 工具都可能读同一篇文档。如果每次直接查库，会出现三类浪费：

1. **并发重复**：同一个 `id` 的 3 个调用同时发现缓存为空，于是发 3 次请求；
2. **重复读取**：第一次已经成功，第二次仍然重新查库；
3. **只缓存不淘汰**：文档越看越多，模块级 Map 只增不减，最后变成内存泄漏。

缓存要同时解决 **重复请求、重复读取、无上限增长** 三件事，只做其中一件都不完整。

## 三、数据结构：两个 Map + 一个上限（40 秒）

| 结构 | key | value | 作用 |
|------|-----|-------|------|
| `pending` | 文档 id | 正在进行的 Promise | 合并同一 id 的并发请求 |
| `values` | 文档 id | 已成功的结果 | 命中缓存，省掉重复读取 |

`values` 不是普通对象，而是 `Map`。原因不是“Map 更高级”，而是这里正好需要：

- key 是任意字符串，不需要担心原型链上的同名属性；
- `Map` 保证插入顺序，`keys().next().value` 永远是最久未使用的那条；
- `delete` 后再 `set`，就能把一条记录移到尾部，天然实现 LRU 的“刷新热度”。

容量默认 200。超过上限时，从 Map 头部删一条，时间复杂度 O(1)。

## 四、一次读取的完整流程

```text
get(id, fetcher)
  |
  +-- pending 命中？ --是--> 直接返回同一个 Promise
  |
  +-- values 命中？ --是--> delete + set 刷新 LRU，返回结果
  |
  +-- 都没命中 -> 创建 request，先放进 pending
                       |
                       +-- resolve -> 写进 values，按容量淘汰
                       |
                       +-- reject  -> 不缓存，允许下一次重试
                       |
                       +-- finally -> 删除 pending 标记
```

关键顺序是 **先放 pending，再真正加载**。这样第二个同 id 调用一定能在 Map 里看到同一个 Promise，
而不是在“检查缓存”和“写入缓存”之间再发一次请求。

```ts
const inFlight = this.pending.get(id);
if (inFlight) return inFlight;

const request = Promise.resolve().then(() => fetcher(id));
this.pending.set(id, request);
```

`Promise.resolve().then(...)` 的作用是把同步异常也变成 rejected Promise；调用方拿到的永远是 Promise，
不会出现“第一次同步 throw、第二次异步 reject”两种形态。

## 五、三个容易漏掉的边界

### 1. 失败不能缓存

网络超时、临时 502 都可能是瞬时问题。把 rejected Promise 存起来，会把一次抖动变成长期不可用。
所以失败只清 pending，不写 values，下一次调用允许重试。

### 2. 失效时，飞行中的旧响应不能回填

假设请求 A 还没回来，用户改名触发了 `invalidate(id)`；随后新请求 B 拉到了新标题。
如果 A 晚到后仍然写缓存，就会用旧数据覆盖新数据。

做法是：`invalidate` 同时删除 `values` 和 `pending`；请求完成时先确认
`pending.get(id) === request`，只有“仍是当前这次请求”才允许写缓存。

### 3. 缓存 key 必须带作用域

代码里的 `id` 是通用 key。真实项目可以：

- 每个用户 / 工作区持有一个 cache 实例；或
- 用 `userId:documentId` 作为 key。

但**缓存隔离不能替代权限校验**。跨用户读取仍必须由后端查询和 RLS 兜底。

## 六、替代方案与取舍（30 秒）

| 我选的 | 替代方案 | 为什么选前者 |
|--------|----------|--------------|
| 应用内两个 Map | 浏览器 HTTP 缓存 | HTTP 缓存不能保证合并并发读取，也不能精确表达“保存后立即失效” |
| 自己封一层 | React Query / SWR | 当前需求只有详情读取，依赖更小；以后有分页、重试、窗口聚焦刷新再换 |
| LRU 200 条 | 无上限 Map | 无上限会把临时访问过的文档永久留在内存，最终变成泄漏 |
| 失败不缓存 | 缓存 Promise / 负缓存 | 瞬时失败容易被放大；如果确实要做负缓存，也必须设很短 TTL |

## 七、面试追问（三个足够）

**Q1：为什么用 Map，不直接用普通对象？**
这里的 key 是文档 id，Map 不经过原型链查找，也不会把 `toString` 这类键和对象原型混在一起；
更重要的是 Map 明确规定插入顺序，删除再插入就能维护 LRU 队列，普通对象的顺序语义不如它可靠。

**Q2：已经有 pending 去重，为什么还要缓存？**
两者解决的时间窗口不同。pending 只合并“请求尚未结束”的并发；请求结束后 pending 就删了，
第二个用户操作仍会重新查库。values 缓存的是“已完成结果”，解决请求串行到达时的重复读取。

**Q3：多标签页或服务端多实例，缓存会不会不一致？**
会，所以它是**单实例内的性能缓存**，不是数据源。写操作成功后主动 `invalidate`；跨标签页可以广播失效事件。
如果要跨实例共享，就上 Redis 一类集中缓存，并明确 TTL 和版本号。安全边界仍然在数据库 RLS。

## 八、2 分钟口述稿

「文档详情读取做了两层缓存。第一层是 pending Map：同一个文档 id 的并发请求只创建一次 Promise，
后面的调用直接复用，避免三处组件同时打开同一篇文档时发三次请求。第二层是 values Map：
成功结果留在内存，第二次读取直接返回；失败不缓存，因为网络抖动不应该变成永久失败。

容量用 LRU 控制在 200 条。Map 的插入顺序就是使用顺序：命中时 delete 再 set，把条目移到尾部；
超过 200 就从头部删最久未使用的一条。这样不会像无上限 Map 一样越积越多。

数据变更时调用 invalidate，同时删缓存和 pending。因为一个旧请求可能在失效后才返回，
完成回调会检查 pending 里的是不是自己，不是就不回填，避免旧数据覆盖新数据。

这套方案解决的是单实例内的重复请求和热读；多标签页、多实例仍以数据库为准，
安全隔离靠 userId 过滤和 RLS。以后如果需求扩展到分页、自动重试、窗口聚焦刷新，
会考虑换成 React Query 或 SWR。」
