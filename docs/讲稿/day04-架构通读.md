## 1. 一句话（10 秒）

MyLotion是一个全栈AI笔记应用，用户可以创建、编辑、管理文档，也可以通过AI进行搜索、读取和操作文档。Supabase负责认证、数据库访问和权限管理，AI Agent通过调用工具来完成相应的具体业务操作，并通过SSE将所有事件实时推送到前端。

## 2. 有哪几块（30 秒）

分为三层：前端,API/Agent层和数据层。前端负责展示文档、编辑内容和解析事件行为；
api/agent层负责身份验证、上下文整理、模型与工具调用；数据层负责数据库访问，保存文档与会话通过用户身份过滤和RLS控制数据访问权限。

## 3. 一句话看懂数据怎么流（20 秒）

一个常见事件：用户对ai说“帮我查找关于性能优化的笔记并归档”。
整个过程可以简化为：用户输入指令->前端发送请求->API验证身份->AI agent搜索笔记->AI agent调用工具归档->数据库更新->通过SSE向前端推送事件更新

# 口述练习

## Q1：前端拿到 SSE 事件后做什么
前提：工具跑在服务端，前端看不到它内部在执行什么 —— 所以事件流是前端唯一的知情渠道。
按事件 type 分四类动作：
类	事件	前端动作
渲染文本	text	追加到 AI 回复气泡（流式打字效果）
展示进度	progress	显示「🔍 搜索笔记」「📝 更新内容」这类工具进度
驱动 UI 动作	note_created / note_modified / confirm_delete	跳转新草稿 / 刷新侧边栏 / 弹确认框（用户点确认后前端才真调删除）
元信息	references / error	渲染引用来源徽标 / 明确报错而非静默断流


答题版：「事件按 type 分发，做四件事——渲染文本、显示进度、驱动 UI 动作、补元信息。」

## Q2：mention 的全链路
用户敲：帮我看看 [@季度总结](9f8c1e2a) 这篇
1. 前端输入（mention-input.tsx）：打 @ 弹文档下拉，选中后把 [@标题](id) 作为纯文本插进输入框（蓝胶囊只是 DOM 显示）
2. 前端 → API：整段原文 POST /api/ai/chat
3. API 层：鉴权 → 幂等落库 → 拉历史 → 把原文原样交给 agent
4. Agent 层：塞进 messages 调 streamText
5. 模型：靠提示词约定识别出 id = 9f8c1e2a
6. 模型调工具：readNote("9f8c1e2a")
7. 数据层：服务端带 userId 查库取 content（RLS 兜底）
8. 回到模型：拿到内容 → 作答
跨了全部三层，但"解析"这件事分散在三个地方，服务端不在其中：前端生成（mention-input）、前端渲染（ai-panel 的 renderMentions，自己一套正则）、模型识别（prompt 约定）。lib/mention.ts 是把协议收敛成可复用实现，不是主链路必经环节。

## Q3：前端怎么知道 + 为什么不让 AI 直接改前端
怎么知道：AI 调 archiveNote → 工具在服务端改库 → 通过 onEvent 上报 note_modified → agent 层入队 → SSE 推前端 → 前端刷新侧边栏。
为什么不让 AI 直接改前端，三层理由：
1. 物理上做不到 —— 工具在服务端的 route handler 里跑，前端状态在浏览器内存里，两个运行环境，服务端拿不到。
2. 旧方案很脆 —— 原来是「共享可变对象 + 轮询」（服务端写 pendingNoteId.current，前端定时读）。多工具写同一个对象有顺序耦合，漏读、时序问题难查。
3. 安全边界 —— 删除这类高危操作，工具只能发起（上报 confirm_delete），真正执行必须由前端在用户点确认后自己调 remove()。模型永远没有直接删数据的权限。
答题版：「工具在服务端执行，前端看不见，所以副作用必须显式上报；用 onEvent 回调取代共享可变对象，前端只消费事件流。顺带这也是权限闸门——危险操作 AI 只能发起、用户才能执行。」
