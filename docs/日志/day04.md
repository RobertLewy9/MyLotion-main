## 今天真正学到的

**C 轨 · EventEmitter**

- `once` 必须「先摘再跑」：反过来写，回调里再 `emit` 同一事件会重入（实测 1 次 vs 5 次）
- 包装函数上挂 `listener` 指回原函数，`off(event, 原函数)` 才能删掉 once 注册的监听器
- `emit` 遍历 `[...list]` 快照：本轮触发集合在开始时定死
- 关键判断：`on` 是原地 `push`（会咬人），`off` 是重建数组（不会）
- **两个"改坏"的实现让原来 10 条用例全绿** —— 用例盖不住语义，得自己补

**B 轨 · 事件循环**

- 铁律：跑完一个宏任务 → 清空微任务（直到空）→ 只有这时才轮到渲染 → 再取下一个宏任务
- **渲染窗口只存在于宏任务之间**。实测：微任务连排 20 万次（11ms）期间，一个 `setTimeout(0)` 完全没机会跑；宏任务递归时它立刻就跑
- `await` 右边的表达式**立即求值**，让位的只是它后面的代码
- `new Promise(executor)` 的 executor **同步执行**
- `return Promise` / `await` thenable 比普通值**多等 2 个 tick**（FIFO 队伍推演见答案文件「附 2」）
- 微任务合并（同一轮去重）≠ debounce（等用户停下来）：3 个不同宏任务各改 1 次，微任务合并会失效（实测 3 次通知）

## 错题本

| 题 | 我的答案 | 正确答案 | 病根 |
|----|----------|----------|------|
| Q3 | `1X2345` | `1 → 3 → 4 → 5 → 2` | `return Promise` 要多等 2 个 tick |
| Q5 | `s1 y1 s2 x y2` | `s1 → y1 → x → s2 → y2` | 以为 `await x()` 会把调用 x 一起推迟 |
| Q6 | `sync m1 m2 m3 t1` | `sync → m1 → m3 → m2 → t1` | 新微任务入队尾，要等本轮已有的跑完 |
| Q8 | `await thenable a b c` | `a → await thenable → b → c` | `await` thenable 多等一轮 |
| Q10 | `1 5 2 3 4` | `1 → 2 → 5 → 3 → 4` | `new Promise` 的 executor 是同步的 |

概念题订正：渲染时机（在**宏任务之间**，不在同步阶段）、微任务无限递归的后果（页面**彻底冻结**且不报错）、宏 / 微任务清单要背全。

> **共同病根：分不清「哪一行是同步执行的，哪一行被推迟了」。**
