# Lotion 架构总览（理解整套流程）

> 目的：面试项目题只考两件事——**你能不能把整个系统讲成一条线**，以及**每个关键决策的取舍**。
> 这份文档把 Lotion 从「用户敲下一个字」到「数据库被改写」的完整链路拆开。
> 读完的产出：一份 2 分钟的口述稿（见 `docs/讲稿/`）。

## 一句话

全栈 AI 笔记应用：**Supabase** 管认证/数据/RLS，**BlockNote** 管富文本，
**DeepSeek Agent** 通过 SSE 事件流实时操作笔记。

## 技术栈

| 层 | 选型 |
|----|------|
| 前端 | Next.js 15（App Router）+ React + Tailwind 4 + shadcn/ui |
| 状态 | Zustand（UI 开关）+ React Context（主题）+ 组件内部 state |
| 编辑器 | BlockNote 0.41（底层 ProseMirror，JSON 数据驱动） |
| 后端 | Next.js Route Handlers（`app/api`）+ Supabase |
| 数据库 | PostgreSQL（单表 `documents` 自引用 + RLS） |
| AI | Vercel AI SDK + DeepSeek，`streamText` 驱动 7 个 Tool |
| 通信 | SSE（AI 事件流） |

## 三层结构

```
┌─ 前端 ──────────────────────────────────────────────┐
│  sidebar(document-list)  │  editor(BlockNote)  │  ai-panel  │
│  树渲染 + 懒加载           │  实时保存 onChange   │  SSE 解析   │
└──────────────┬──────────────────────┬───────────────┘
               │ supabase-js          │ fetch POST /api/ai/chat
┌──────────────▼──────────────────────▼───────────────┐
│  API 层  route.ts：鉴权 → 幂等落库 → 拉历史 → 跑 Agent │
├─────────────────────────────────────────────────────┤
│  Agent 层  agent.ts：streamText + 7 Tool + onEvent   │
│  lib/ai/tools/*：search/read/create/update/rename/   │
│                  archive/delete                      │
│  lib/compress.ts：滑动窗口 + 摘要压缩                 │
└──────────────┬──────────────────────────────────────┘
               │ supabase-js（service 权限 + userId 过滤）
┌──────────────▼──────────────────────────────────────┐
│  数据层  documents（parentDocument 自引用 + RLS）      │
└─────────────────────────────────────────────────────┘
```

## 主链路：用户问一句「帮我找关于性能优化的笔记并归档」（端到端）

1. **前端** 把输入框内容 + `sessionId` + `requestId` POST 到 `/api/ai/chat`
2. **route.ts**
   - `supabase.auth.getUser()` 鉴权，未登录 → 401
   - 校验会话归属（`sessionId` + `userId`）
   - 落库 user 消息，`requestId` 命中唯一约束 → 409（**幂等去重**）
   - 首条消息自动命名会话
   - 拉取该会话**未压缩**的最近 `WINDOW_SIZE`(100) 条历史 + 会话摘要
3. **agent.ts** 组装 `messages`（历史 + summary + 当前输入），调 `streamText({ model, tools, stopWhen: 5 步 })`
4. **模型决定调工具** → `searchNotes`（服务端 `ILIKE` 模糊匹配标题，返回 id + 标题 + 摘要）
5. 模型拿到结果 → 调 `archiveNote` → 工具内部经注入的 **`onEvent` 回调**上报 `note_modified`
6. **agent 层**把事件塞进 `eventQueue`；SSE 包装层用 **200ms 轮询**把队列取出，编码成 `data: <json>\n\n` 推给前端；文本 delta 走 `text` 事件
7. **前端 ai-panel** 按 `\n\n` 切分行、`JSON.parse`，按 `type` 分发：`progress` 显示进度、`note_modified` 刷新列表、`confirm_delete` 弹确认框
8. 流结束后，`done` promise resolve → 后台落库 assistant 消息（含 token 统计）→ 触发 `maybeCompressSession`

**关键点：工具跑在服务端，前端看不到它的内部执行**，所以必须靠 `onEvent` 显式上报副作用
（旧方案是「共享可变对象 + 轮询」，多工具写同一对象有顺序耦合，已废弃）。

## 四条链路拆开看

### ① 数据层：无限层级文档树

- 单表 `documents`，`parentDocument` 自引用，任意深度
- 侧边栏用 `getSidebarAll()` **一次性拉全量扁平数组**（避免 N 次查询），前端再还原成树
- 归档/恢复递归子节点；删除高危操作由 RLS + userId 过滤兜底

### ② AI 链路：Tool 编排

- 7 个 Tool：search / read / create / update / rename / archive / delete
- **危险操作有确认闸门**：`deleteNote` 不真删，只上报 `confirm_delete`，
  用户确认后前端才调 `remove()` —— 「AI 只能发起，用户才能执行」
- **防重复建草稿**：`createNote` 闭包内维护 `createdNoteId`，工具实例按请求创建，
  闭包状态天然按请求隔离 + 提示词软约束「每轮最多建一篇」
- **工具统一包装** `withToolLogging`：try/catch 捕获异常并给 AI 返回**可读错误字符串**（让模型自己重试），
  每个工具 30s 显式超时防挂起

### ③ 上下文：滑动窗口 + 摘要压缩

- 结构：`[系统提示词] + [历史摘要] + [最近 100 条原文] + [当前输入]`
- 窗口是**确定性**的（不交给模型挑选保留哪些），模型只负责把窗口外的消息总结成摘要
- **重写式**摘要（旧摘要 + 本次滑出消息 → 新摘要），先写摘要再标记消息，避免「已标记但没摘要」
- 失败一律降级为「本轮不压缩」，按会话串行化（Promise 链）防并发覆盖

### ④ 性能与权限

- 文档详情：`getById` 做了**请求去重**（同一个文档并发请求共用一个 promise）+ **内存缓存**（上限 200 条，LRU 淘汰）
- 侧边栏树渲染：`useMemo` 缓存树结构，避免每次 render 重新递归
- 移动端 sidebar 自动折叠（监听路由）
- 权限：未发布文档由 **RLS** 拦截，跨用户查询带 `.eq("userId", userId)`

## 关键取舍（面试官最爱追问的「为什么不用 X」）

| 决策 | 为什么 | 替代方案 / 面试怎么答 |
|------|--------|----------------------|
| SSE 而非 WebSocket | **单向**推送（服务端 → 前端）、基于 HTTP 无需额外协议升级、自动重连、穿透代理友好 | "如果要做**双向**实时协同编辑，我会换 WebSocket；协作场景两者都要上" |
| 事件回调而非共享可变对象 | 多工具写同一对象有顺序耦合；事件类型显式可枚举，新增副作用不会漏推 | 讲清楚旧方案的痛点 |
| 单表自引用而非邻接表 | 层级简单、查询少；全量拉回内存建树 `O(n)` | 深度极大时考虑闭包表 / 路径枚举 |
| 危险操作二次确认 | 模型永远没有直接删除权限，杜绝误删 | 幂等键 + RLS 双保险 |
| 摘要压缩而非全量注入 | 控制 token 成本，同时保留早期决策 | CRDT 是**协同**问题，压缩是**上下文**问题，别混 |
