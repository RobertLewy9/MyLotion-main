# Day 8 · B2 轨 —— Agent 运行时：循环、重试与确认闸门（问答一体）

> **归属：Day 8 · B2 轨（Agent 八股）**
> 依据：现场真正追问的是「一句话改一篇笔记怎么跑起来」「工具失败怎么办」「删错了怎么办」。
> 用法：主链路按“① 干什么 → ② 完整流程 → ③ 为什么这样设计”回答；概念题先给结论再补机制。

## 思维导图

```text
Agent 运行时
├─ 循环：模型决策 → 服务端执行 → 结果回填 → 再决策
├─ 停止：最终答案 / 最大步数 / 超时与预算 / 用户取消 / 不可恢复错误
├─ 失败：参数错误 / 业务未命中 / 权限错误 / 瞬时故障 / 超时
├─ 幂等：requestId / operationId / 数据库唯一约束与事务
└─ 危险操作：预览 → 用户确认 → 服务端复校验 → 只执行一次
```

## Part 1 · 概念

### Q1. 一次普通模型调用和 Agent Loop 有什么区别？靠什么继续和停止？怎样防止无限循环？

**参考答案（口述）**

一次模型调用是输入一次、输出一次；Agent Loop 是模型决定调用工具，服务端执行后把结果交回模型，模型继续判断，直到任务结束。

```text
用户输入
  → 模型判断
      → 不调用工具：输出最终答案，结束
      → 调用工具：服务端执行
          → 工具结果回填模型
          → 模型继续判断
```

**停止条件：**

1. 模型输出最终答案，不再调用工具；
2. 达到最大步数，例如 8 步；
3. 超过时间或 token 预算；
4. 用户主动取消，或遇到不可恢复错误。

**工程护栏：** 设置最大步数和超时，检测重复工具调用，参数错误只允许有限次纠正。

**顺便区分 Workflow：** Workflow 的步骤由代码提前规定；Agent 的下一步由模型根据执行结果动态决定。

### Q2. 工具失败、超时或被重复调用怎么处理？哪些错误回填，哪些必须终止？

**参考答案（口述）**

模型提出工具调用，服务端负责参数校验、权限检查、执行和错误处理。

| 错误类型 | 处理方式 |
|---|---|
| 参数错误 | 返回错误信息，让模型有限次纠正 |
| 业务未命中 | 返回正常结果，让模型换策略或告知用户 |
| 权限错误 | 拒绝操作，不能让模型反复尝试 |
| 瞬时故障 | 读操作可有限重试；写操作必须幂等 |
| 超时 / 取消 | 停止后续执行，取消下游请求 |

**幂等：** 同一个操作执行一次和执行多次，最终效果相同，避免重复创建、修改或删除。

三层保障：

1. `requestId`：防止同一次用户请求启动多个 Agent；
2. `toolCallId / operationId`：识别工具调用或业务操作，重试时复用稳定操作 ID；
3. 数据库唯一约束 / 事务：防止重复写入，作为最终保障。

**记住：** 网络请求可能重复到达，但业务副作用只能发生一次。

### Q3. `deleteNote` 为什么不能由模型直接执行？怎样设计 human-in-the-loop？

**参考答案（口述）**

模型可以提出删除请求，但不能直接执行不可逆操作，必须经过用户确认和服务端再次校验。

**为什么需要确认：**

- 模型可能理解错用户意图；
- 用户可能没意识到删除范围；
- 模型可能受到提示注入影响。

**两阶段确认：**

```text
模型调用 deleteNote
  → 服务端校验参数，不执行删除
  → 生成待确认操作和确认信息
  → SSE 通知前端弹出确认框
  → 用户点击确认
  → 前端提交确认请求
  → 服务端再次校验权限、资源状态和确认 token
  → 执行删除，记录审计日志
```

**关键点：**

- 第一次调用只生成待确认操作，不产生删除副作用；
- 确认 token 绑定用户和资源，设置有效期，只能使用一次；
- 用户确认后，服务端必须重新检查权限和资源状态；
- 重复确认通过幂等机制避免重复执行；
- 批量删除必须明确展示影响范围。

## Part 2 · 项目落地

### Q. 按“① 我项目里干什么 → ② 完整流程 → ③ 为什么这样设计”讲清 MyLotion 的 Agent 主链路

**参考答案（口述）**

**① 我项目里干什么：** 用户说“把 Q3 计划里的时间改成下周五”，Agent 要搜索文档、读取内容、修改字段，并把变化实时反映到前端。

**② 完整流程：**

```text
前端提交问题 + requestId
  → /api/ai/chat
  → 鉴权、幂等检查、组装上下文
  → streamText 启动 Agent Loop
  → 模型判断下一步
      → 需要调用工具
          → 服务端校验参数和 userId
          → 执行工具
          → 工具结果回填模型
          → 回到模型继续判断（循环）
      → 不需要调用工具
          → 模型生成最终答案
          → 通过 SSE 流式传给前端（SSE，Server-Sent Events，服务器发送事件）
          → 前端展示完整回答
          → 服务端结束本次流式响应
          → 保存对话记录、更新运行状态
```

**副作用如何通知前端：**

- `onEvent` 上报工具执行过程中的事件；
- SSE 把事件推送到前端；
- `note_modified` 通知刷新文档列表；
- `confirm_delete` 通知弹出删除确认框。

删除工具第一次调用只产生 `confirm_delete` 事件，不直接删除数据库数据。

**③ 为什么这样设计：**

模型只负责决策，服务端负责权限、参数、事务和副作用控制；前端通过事件感知变化；危险操作保留最终人工确认。

### 面试追问

**用户连点两次发送怎么办？**

前端可以禁用按钮，但真正保障在服务端：用 `requestId` 做幂等检查，重复请求返回已有运行状态，不再启动新的 Agent。

**确认框被点两次怎么办？**

确认 token 只能消费一次，数据库通过事务和幂等机制保证删除不会重复执行。

**为什么不在 `deleteNote` 工具里直接删除？**

模型不应拥有不可逆操作的最终执行权。先生成待确认操作，让用户看到范围，确认后再由服务端检查权限并执行。

## 30 秒复盘

MyLotion 的 Agent 循环是：模型决定调用哪个工具，服务端校验参数和用户权限后执行，再把结果回填模型，直到模型输出最终答案。运行时设置最大步数和超时，工具失败按参数、权限、瞬时故障分类，重复操作通过 `requestId`、operationId 和数据库约束保证幂等。删除等危险操作第一次只生成 `confirm_delete`，用户确认后服务端再次校验并只执行一次。
