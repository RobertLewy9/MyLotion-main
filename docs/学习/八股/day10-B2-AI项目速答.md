## Part 1 · 概念与项目全景

### Q1. 用 60 秒介绍 Lotion，并说清它的三条主链路。

**参考答案（口述）**

Lotion 是一个单机自托管的 AI 笔记应用。前端是 Vite 8 + React 19 SPA，后端是 Hono 4，Node 单进程同时提供 REST API、静态资源和 SPA 回退；数据落在本地 SQLite，编辑器是 BlockNote，AI 用 Vercel AI SDK 接 DeepSeek。

三条链路：

1. **文档链路**：组件不直接 fetch，而是走 `docStore` 接缝；浏览器实现调用 REST，宿主实现直接访问 SQLite。文档结构以 BlockNote JSON 保存。
2. **AI 链路**：前端 `POST /api/ai/chat` → `requireAuth` → 幂等校验 → 组装上下文 → `streamText` → 模型选择工具 → 服务端执行 → SSE 把文本和副作用事件推回前端。
3. **插件链路**：Cordis 内核负责装配，`docStore / settings / httpRoutes / tools / uiSlots / remote / dynamicPlugins / pluginAdmin` 八条接缝隔离能力，插件注册必须带可逆 disposer。

**一句话收尾：** 这个项目最关键的不是“接了一个大模型”，而是把模型能力放进一条可控的服务端工具链里：权限、校验、审计、确认和撤销都由应用负责。

### Q2. Tool Calling 是什么？模型和服务端各自负责什么？

**参考答案（口述）**

Tool Calling 是让模型输出结构化的“我要调用哪个工具、参数是什么”，而不是直接操作数据库。

```text
用户输入 → 模型判断
  → 需要动作：输出 tool call
  → 服务端校验参数、userId、权限和超时
  → 执行工具，把结果作为 tool 消息回填
  → 模型继续判断，直到给出最终答复
```

**边界必须说清：**

- 模型只负责**选工具、填参数**；
- 真正执行、鉴权、数据库访问、超时和错误处理都在服务端；
- 工具结果不是“模型自己知道”，而是应用把它回填进下一轮上下文；
- 写操作要考虑幂等，危险操作要有人机确认。

Lotion 当前有 19 个内置工具，按四类理解：

| 类别 | 例子 | 作用 |
|---|---|---|
| 检索 | `searchNotes` / `listNotes` / `readNote` / `listTrash` / `getDocInfo` / `getDocOutline` / `getDocBlocks` | 找文档、读正文、查结构与回收站 |
| 写入 | `createNote` / `updateNote` / `updateBlock` / `setNoteIcon` | 创建或修改文档内容与图标 |
| 组织 | `renameNote` / `moveNote` / `publishNote` / `archiveNote` / `restoreNote` / `deleteNote` | 调整位置、发布状态和生命周期 |
| 交互 | `askUser` / `todoWrite` | 向用户提问、维护任务清单 |

**一句话：** 模型是决策器，不是数据库客户端；工具是受控的能力边界。

### Q3. 为什么用 SSE，不用 WebSocket？事件流怎么走？

**参考答案（口述）**

这里的通信主要是**服务端到客户端的单向推送**：文本增量、工具开始/结束、笔记变更、确认请求和错误。浏览器不需要在同一个连接上持续回消息，所以 SSE 足够。

**SSE 的优点：**

- 基于普通 HTTP，不需要协议升级；
- 浏览器和代理兼容性好；
- 自带断线重连语义；
- 实现比 WebSocket 简单，调试时直接看 `data: <json>` 行。

**代价：** 不能双向通信。如果要做多人实时协同编辑，WebSocket 或 CRDT 同步更合适；当前 AI 对话是“客户端发一次 HTTP，服务端持续推结果”，SSE 正好匹配。

**Lotion 的事件流：**

```text
工具执行 → onEvent 上报副作用
  → eventQueue
  → SSE 包装层每 200ms 检查队列并立即提交
  → data: <json>\n\n
  → 前端按事件 type 分发：渲染文本 / 刷新列表 / 显示进度 / 弹确认框
```

**注意：** 200ms 是服务端事件队列的兜底唤醒间隔，不是前端轮询数据库。数据变化由服务端主动推送。

### Q4. 上下文太长怎么办？为什么现在不做 RAG？

**参考答案（口述）**

模型本身无状态，多轮对话靠每一轮重新组装 `messages`。上下文一旦无限增长，会带来三个问题：成本上升、延迟增加、关键信息被淹没。

Lotion 当前用**滑动窗口 + 重写式摘要**：

1. 最近 100 条未压缩消息保留原文；
2. 滑出窗口的旧消息交给模型压缩成摘要；
3. 下一轮上下文 = 系统提示词 + 历史摘要 + 最近窗口 + 当前输入；
4. 先写摘要成功，再标记旧消息已压缩，避免“标记了却没摘要”。

**为什么现在不做向量 RAG：** 当前是个人笔记规模，用户通常围绕当前文档或近期会话提问；滑动窗口加摘要已经能覆盖主要场景。上 RAG 需要额外的 embedding、向量库、切片、权限过滤和评测，复杂度和运维成本明显更高。

**什么时候该上 RAG：** 笔记量很大、需要跨大量文档做语义检索、用户明确问“我以前在哪篇笔记写过……”且关键词搜索不够时，再引入 RAG。面试时要说“当前现状”和“演进条件”，不要把设计说成已上线。

### Q5. 为什么直接定义工具，不急着上 MCP？

**参考答案（口述）**

MCP 解决的是**Host 如何用统一协议发现和连接外部工具/数据源**；Function Calling 解决的是**模型如何表达要调用什么**。两者不是替代关系。

Lotion 当前 19 个工具都跟业务强耦合：查笔记、改文档、删除、发布。它们直接定义在服务端有三个收益：

1. 权限、事务、审计和错误处理都在同一个进程里；
2. 不需要额外部署 MCP Server，延迟和调试链路更短；
3. 工具 schema 与内部数据模型可以一起演进。

**什么时候值得上 MCP：** 要接 Notion、GitHub、云盘、企业知识库，或者同一批工具要服务多个 AI 客户端时，标准化收益才会超过接入成本。第三方 MCP 还要做白名单、版本固定、凭证隔离、返回内容限流和危险操作确认。

## Part 2 · 项目落地

### Q6. 按「一句话改一篇笔记」讲完整链路。

**参考答案（口述）**

1. 用户说“把 Q3 计划里的时间改成下周五”。
2. 前端把 `prompt`、`sessionId`、`requestId` 和当前文档信息 POST 到 `/api/ai/chat`。
3. Hono 先经过 `requireAuth`，从 HttpOnly session cookie 取当前用户；再校验会话归属。
4. 用 `requestId` 做幂等：消息表有唯一约束，重复请求返回 409，不重复执行。
5. 服务端组装系统提示词、历史摘要、最近窗口和当前输入，调用 `streamText`。
6. 模型先调用 `searchNotes` / `readNote` 找到目标文档。
7. 服务端校验参数和 `userId`，执行工具并回填结果。
8. 模型决定调用 `updateNote` 或 `updateBlock`，服务端执行写操作。
9. 工具通过 `onEvent` 上报 `note_modified`，事件进队列，再由 SSE 推给前端。
10. 前端刷新侧边栏或编辑器；写操作前的快照进入 `ai_changes`，支持本轮撤销。
11. 模型输出最终答复；`turn_end` 后落库 assistant 消息和回合快照，必要时触发上下文压缩。

**关键点：** 模型没有直接数据库权限；它只是提出动作，应用决定能不能执行。

### Q7. 删除、越权和失败怎么兜底？

**参考答案（口述）**

**删除：** `deleteNote` 不直接删除，只上报 `confirm_delete`；前端弹框，用户确认后才执行真正删除。原则是“AI 只能发起，用户保留执行权”。

**越权：** SQLite 没有 RLS，所以所有 SQL 都在应用层显式带 `userId`；REST 路由统一经过鉴权和会话归属校验。模型即使生成了别人的文档 ID，服务端查询也查不到。

**失败：**

- 参数错误：把可读错误回填模型，允许有限次纠正；
- 权限错误：直接终止，不允许反复尝试；
- 超时：每个工具有显式超时，避免挂起；
- 重复调用：`requestId`、唯一约束和工具幂等共同兜底；
- 死循环：Agent 最多 5 步，并用 doom loop 检测重复失败。

**撤销：** 隐式写入前保存文档快照到 `ai_changes`，按 `requestId` 分组；用户显式确认过的删除/移动不再走自动撤销。

## 30 秒复盘

Lotion 是单机自托管的 AI 笔记应用：Vite SPA 负责界面，Hono 单进程提供 API 和静态资源，SQLite 存文档与会话，BlockNote 存结构化 JSON。AI 链路是 `POST /api/ai/chat` → 鉴权和幂等 → 组装上下文 → `streamText` → 模型从 19 个工具中选动作 → 服务端执行 → `onEvent` / SSE 推回前端。模型只决策，服务端负责权限、校验、执行和审计；删除走确认闸门，写入前存快照，重复请求用 `requestId` 防重。上下文目前用 100 条窗口加摘要，RAG 和 MCP 都按明确触发条件再引入。
